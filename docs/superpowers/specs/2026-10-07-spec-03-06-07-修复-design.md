## 1. 背景

`docs/specs/` 下的 11 份 SPEC 是 2026-10-07 对全仓的系统性缺陷审计。SPEC-01（网关路由）与 SPEC-02（数据层 DDL）已完成。本设计覆盖剩余 P0/P1 中的三份：

| SPEC | 功能域 | 为什么在这一批 |
|------|--------|----------------|
| SPEC-03 | 秒杀主链路正确性 | P0。库存双扣、消息静默丢失、消费失败静默 ACK，直接造成资金/库存错误 |
| SPEC-06 | 鉴权与越权防护 | P1。业务服务零鉴权，内部扣库存端点裸露 |
| SPEC-07 | Feign 契约与服务间调用 | P1。`/user/list` 不存在导致点赞榜与共同关注必然不可用 |

**SPEC-06 与 SPEC-07 必须同批实施**：SPEC-06 为业务服务加装拦截器后，order→voucher、social→user、agent→rag 未适配的 Feign 调用会被拒绝，秒杀与检索链路会整体中断。二者存在强耦合。

### 1.1 缺陷复核结论

动手前已逐条复核三份 SPEC 对 `master@531266c` 的断言，**全部仍然成立**，无过期条目：

- `seckill.lua:35` 的 `DECR` 与 `VoucherServiceImpl.java:75` 的 `decrement` 构成双扣；
- `SeckillOrderProducer.java:75-100` 的 `asyncSend` 回调失败仅记日志，`VoucherOrderServiceImpl.java:129` 无论成败返回 `Result.ok`；
- `SeckillOrderConsumer.java:93` 锁失败 `return`（= ACK 丢弃）、`:111`/`:119` 回滚误用 `increment`、`:141` 抛异常触发无幂等的重试；
- `common/.../SaTokenConfig.java` 是空类，全仓 `SaInterceptor`/`addInterceptors` 零命中；
- `UserFeignClient.java:28` 的 `@GetMapping("/user/list")` 在 `UserController` 中无对应映射（会被 `/user/{id}` 捕获后 `Long` 转换失败）；

此外复核中发现**一处 SPEC-03 正文未列出、但 README §2.1 明确派给 SPEC-03 的前置项**：订单明细 key 在删除端拼错（详见 §A7），必须在本批冻结契约，否则 SPEC-04 的对账会读到错误 key。

## 3. 关键决策

SPEC 原文留有选择空间、或本设计需要补充判断的 7 处，均已与需求方确认：

| # | 决策 | 取舍理由 |
|---|------|---------|
| D1 | `deductStock` 的幂等键用 **Redis Set**（`seckill:deduct:{voucherId}`），不新建 `tb_stock_deduct_log` 表 | SPEC-03 §5.4 明确认可"新增表**或**复用 Redis Set"。不引入 DDL 变更（与 SPEC-02 改动面解耦），符合"简单优先" |

| D3 | 内部端点用**独立 `InternalVoucherController`**，而非在 `VoucherController` 内写 `/internal` 路径 | `VoucherController` 类级前缀是 `/voucher`，方法级写 `/internal/...` 会拼成 `/voucher/internal/...`。独立 Controller 同时实现 SPEC §5.2 期望的物理隔离 |

## 4. Workstream A — SPEC-03 秒杀主链路正确性

### A1. `seckill.lua`

- `stock == nil` 分支由 `return 1` 改为 `return 3`（G5：把"key 缺失"与真实"库存不足"分开）。
- 补注释：`seckill:stock:{voucherId}` 的**唯一 owner 是 order-service**，voucher-service 不得再操作该 key。
- **`DECR` / `SISMEMBER` / `SADD` / `HSET` 的原子逻辑保持原样**（SPEC-03 §1.1 确认其正确）。

### A2. `VoucherServiceImpl.deductStock`

- 删除 `stringRedisTemplate.opsForValue().decrement(SECKILL_STOCK_KEY + voucherId)`（消除双扣，G1/A7）。
- 补 `@Transactional`（修复 SPEC-03 §1.8 的两步非原子）。
- 签名增加 `orderId`，实现服务端幂等（D1）：

```java
@Override
@Transactional
public Result deductStock(Long voucherId, Long orderId) {
    String key = SECKILL_DEDUCT_KEY + voucherId;
    Boolean first = stringRedisTemplate.opsForSet().add(key, orderId.toString());
    if (Boolean.FALSE.equals(first)) {
        return Result.ok();                      // 该订单已扣过，幂等返回
    }
    boolean success = seckillVoucherService.update()
            .setSql("stock = stock - 1").eq("voucher_id", voucherId).gt("stock", 0).update();
    if (!success) {
        stringRedisTemplate.opsForSet().remove(key, orderId.toString());  // 未扣成功，放开标记
        return Result.fail("库存不足");
    }
    return Result.ok();
}
```

> 行为核对：消费重试时 `selectById(orderId)` 未命中 → `SADD` 返回 0 → 直接返回成功 → 插单。DB 库存净减 1，G4/A6 成立。

- 保留 `StringRedisTemplate` 注入（`addSeckillVoucher` 写初始库存、此处幂等标记均需）。
- `RedisConstants` 新增 `SECKILL_DEDUCT_KEY = "seckill:deduct:"`。

### A3. `VoucherOrderServiceImpl.seckillVoucher`

| 改动 | 目标 |

### A4. `SeckillOrderConsumer`

| 位置 | 现状 | 修正 |
|------|------|------|

### A7. 冻结订单明细 key 契约（README §2.1 派给 SPEC-03 的前置项）

复核时新发现：订单明细 key 在写入端、删除端、读取端有**两种不同拼法**——删除端是错的。

| 角色 | 位置 | 拼法 | 是否正确 |
|------|------|------|---------|
| 写入 | `seckill.lua:16` | `seckill:order:detail:{voucherId}` | ✅ 权威 |
| 删除 | `SeckillOrderConsumer.java:135` | `SECKILL_STOCK_KEY + "order:detail:" + voucherId` → `seckill:stock:order:detail:{voucherId}` | ❌ 永不命中 |
| 读取 | `SeckillConsistencyServiceImpl.java:42` | `"seckill:order:detail:"` | ✅ |

**后果**：消费者删的是永不存在的 key，真实明细 hash 只增不减、永久残留；且 SPEC-04 的对账逻辑要读这个 key，契约不冻结会让它对不上账并制造二次脏数据。README §2.1 因此规定"3 必须先于 4"。

**修正**（以写入端为准，它是权威产生方）：

- `RedisConstants` 新增三个常量，成为唯一来源：`SECKILL_ORDER_DETAIL_KEY = "seckill:order:detail:"`、`SECKILL_ORDER_SET_KEY = "seckill:order:"`、`SECKILL_DEDUCT_KEY = "seckill:deduct:"`。
- `SeckillOrderConsumer.java:135` 改用 `SECKILL_ORDER_DETAIL_KEY + voucherId`（**修掉删除端拼错**）。
- `SeckillOrderConsumer` 的 `SREM` 与 A3 的 `rollbackSeckillReservation` 一律改用常量。
- `SeckillConsistencyServiceImpl.java:42` 的字面量替换为同一常量——**取值不变，纯契约单源化，行为零变化**（不碰该类的任何逻辑，其业务缺陷仍归 SPEC-04）。

## 5. Workstream B — SPEC-06 鉴权与越权防护

### B1. `common/.../config/SaTokenConfig` 空类 → 真实配置

```java
@Configuration
@ConditionalOnWebApplication(type = Type.SERVLET)
@ConditionalOnClass(SaInterceptor.class)
public class SaTokenConfig implements WebMvcConfigurer {
    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(new SaInterceptor(handle -> StpUtil.checkLogin()))
                .addPathPatterns("/**")
                .excludePathPatterns("/user/login", "/user/code",
                                     "/internal/**", "/actuator/**", "/error");
    }
}
```

### C1. 补齐 `/user/list`（G1、G2）

`UserController` 新增：

```java
@PostMapping("/list")
public Result queryUserByIds(@RequestBody List<Long> ids) {
    if (ids == null || ids.isEmpty()) return Result.ok(Collections.emptyList());
    if (ids.size() > 100) return Result.fail("批量查询数量不能超过 100");
```

### 10.3 起全栈的关键前提（否则会得出错误结论）

1. **中间件不是可选项、也不会自动就绪**：Redis、RocketMQ **4.9.4**、Nacos（standalone）、MySQL 8 必须全部先起，再启动服务。
2. **Java 必须是 21**。本机 `PATH` 上的 `java` 是 **17**，而构建目标为 class file major 65（`java.version=21`，§1 基线）；服务须用 Java 21 二进制显式启动。本机 `JAVA_HOME=D:\Config\java` 指向 21.0.7，`PATH` 上的 `java` 却是 `.jdks/ms-17.0.18`——用 `JAVA_HOME` 或绝对路径，勿依赖 `which java`。
3. **启动服务前必须加载 `.env`**：`set -a; source .env; set +a`。否则 `INTERNAL_TOKEN` 为空，按安全默认所有 `/internal/**` 返回 401，秒杀链路必然失败（§8 已列）。
4. **`.env` 的 `ADMIN_USER_IDS` 必须设为你登录用户的 id**，"管理员得 200"那半才会通过。当前值为 `1`（已核对），新注册测试用户不会被命中——403 那半仍通过，200 那半不通过。
5. **网关鉴权过滤器在路由之前短路**：不带 token 时对**任意**路径（含无路由路径）都返回 HTTP 200 + `{"success":false,"errorMsg":"未登录，请先登录"}`。因此任何不带 token 的可达性检查都是**假绿**，测路由可达性必须带 token（与 §7.2 陷阱同源）。

### 10.4 已知残留

- **`syncSend` 3 秒超时**：broker 已收下消息但发送调用超时，入口按"未发出"回滚 Redis 预扣，消费者却照常消费成功——该场次 Redis 库存多 1、`Redis 库存 + 成功订单数 == 100` 不成立，DB 库存仍正确。见 §8，彻底消除归 SPEC-04。
- **幂等标记在 DB 事务之外**：Redis `SADD` 与 DB 扣减之间崩溃会造成静默少卖 1 件。选 Redis Set 方案时已接受（§3 D1）。

### 10.5 一处值得点名的复核结论

终审时有人提出：`queryMyOrders` 对 Feign 返回体做的 `(Map<?, ?>)` 强转会抛 `ClassCastException`，导致生产环境券字段恒为 null。**该主张被驳回**：`Result.data` 声明为 `Object`（已核对 `common/.../utils/Result.java:15`），Jackson 反序列化后是 `LinkedHashMap`，强转正确；且该模式在 N+1 重构之前就存在。

> 但**只有端到端实跑能证伪这段推理**——单测里 Feign 被 mock，走的不是 Jackson 反序列化路径。下次拉起全栈时，应把"下单后 `GET /voucher-order/my` 返回的券标题/面额非空"作为一项显式检查（即 A9 N+1 消除的正确性断言，§7.2 未单列，此处补记）。
