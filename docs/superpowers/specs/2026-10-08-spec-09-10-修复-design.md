## 3. 与 SPEC 正文的偏离（7 处，已获用户裁定）

用户于本轮开工前对以下 7 项逐条裁定，全部照此执行。

| # | 偏离 | 理由 |
|---|---|---|
| **P1** | **不实现 SPEC-09 §5.4 的"大 V 阈值切换拉模式"** | 该片段 `if (followerIds.size() > LARGE_V_FANOUT_THRESHOLD) return;` 会把大 V 的动态对其全部粉丝**静默丢弃**——因为 `queryBlogOfFollow` 只读收件箱 ZSet，跳过 fan-out 就等于该动态永不出现在任何人的关注流里。要让阈值成立必须同时实现读取端合并，而 SPEC-09 §1.12 明确「**不是要改成拉模式**」。验收 A8 只要求"响应时间与粉丝数解耦"，异步化已完全满足。 |
| **P2** | **取消点赞分支"始终 `ZREM`"**，而非 SPEC-09 §5.2 片段的 `if (!isSuccess) return fail` | 片段写法下存在死锁态：若 DB 的 `liked` 已被新增的 `gt("liked", 0)` 守卫挡回（=0），而 Redis ZSet 中仍有该用户，则用户此后**永远无法取消点赞**（每次都因守卫失败而直接 return，`ZREM` 永不执行）。始终执行 `ZREM` 使两侧收敛到"未点赞"，且**仍满足 A4「liked 在任何序列下 ≥ 0」**。 |
| **P3** | 退款：**`refund_time` 语义与 5 的终态化**（方案 B 变体） | 保留原子 `2 → 5`，把状态机定义降级为「5-退款受理（终态，资金线下流转）」，从 DDL 注释与 README 中删除**从未被任何代码写入过**的 6。理由：E4 已确立产品语义是"线上受理 + 线下资金流转"，`ConfirmService` 成功文案即"预计 1-3 个工作日原路退回"。若按字面"退款直接置 6"，用户订单卡片会**立即显示「已退款」而资金尚未到账**，属于对用户输出错误信息。A7 走其"**或**描述已如实降级"分支，以 DDL 注释 + README + 实测断言交付。 |
| **P4** | **不改 `ShopServiceImpl` 的 `ORDER BY FIELD` 拼接** | SPEC-09 §1.10 引用的 `:488` 已漂移到 `:162`，且该行位于 `queryShopByType` 的 GEO 检索路径，而 SPEC-05 §1.12 明令「商户 GEO 附近查询…**不改检索逻辑**」（SPEC-05 已交付）。该处 `ids` 与 social 侧同源（系统写入的 Redis ZSet 值），注入风险同等低。本轮只改 social 的 `BlogServiceImpl:221`。 |
| **P5** | **`RedisIdWorker` 的时区两行保持原样** | SPEC-10 §5.1 的"修复代码"本身就没有改 `toEpochSecond(ZoneOffset.UTC)` 与本地 `date` 两行——唯一实质修复是回拨守卫。若按"要点"改写（改用真实纪元秒），`timestamp` 将整体位移 28800 秒，使**新订单 ID 小于部署前的旧订单 ID**，而仓库中存在 `ORDER BY id` 的用法（`agent-service` 对账测试即按此快照）。且分片键只切分计数空间：ID 冲突需 `(timestamp, count)` 同时相等，而 timestamp 随墙上时钟严格递增、count 在同一 key 内严格递增，故原实现**并非正确性缺陷**。改动只有风险没有收益。 |
| **P6** | 给 `social-service` 补 `spring-boot-starter-test` 依赖（`test` 作用域） | E1：SPEC-09 §8.8 要求 `mvn -pl social-service,order-service,shop-service test`，而该模块没有任何测试基础设施。依赖声明是执行该验收的必要条件。 |
| **P7** | 分页下限两处策略不同：**social 用 `Math.max(current,1)`（→200）**，**shop 用 `@Min(1)`（→400）** | A11 明确断言 `GET /blog/hot?current=0` **返回 200 且不抛异常**，故 social 不能走 400 路线；而 shop-service 已在 SPEC-05 A7 建立了 `@Min` + `ShopValidationExceptionHandler` → 400 的范式（并已有 `ShopControllerValidationTest` 覆盖），沿用可保持模块内一致。SPEC-09 §5.5 原文即写「补 `@Min(1)`（**或**服务端 `Math.max(current, 1)`）」，两者均在授权范围内。 |

### A2. 点赞一致性（G2/G3；A4/A5/A6）

**`social-service/.../service/impl/BlogServiceImpl.java`**

`likeBlog(Long id)`：

```
1. UserDTO user = UserHolder.getUser();  为空 → Result.fail("未登录")
2. Blog blog = getById(id);              为空 → Result.fail("博客不存在")   // A5
3. key = BLOG_LIKED_KEY + id
4. score == null（未点赞）:

public void submit(Long blogId, Long authorId) {
    try {
        executor.execute(() -> fanOut(blogId, authorId));
    } catch (RejectedExecutionException e) {          // 兜底：策略可换，保证不冒出到调用方
        log.error("Feed 推送任务提交失败: blogId={}, authorId={}", blogId, authorId, e);
    }
}

private void fanOut(Long blogId, Long authorId) {
    try {
        List<Long> followerIds = followService.queryFollowerIds(authorId);
        String blogIdStr = blogId.toString();
        for (Long fid : followerIds) {
            String key = FEED_KEY + fid;
            stringRedisTemplate.opsForZSet().add(key, blogIdStr, System.currentTimeMillis());
            stringRedisTemplate.expire(key, FEED_KEY_TTL_DAYS, TimeUnit.DAYS);   // 僵尸收件箱不再永驻
        }
    } catch (Exception e) {
        log.error("Feed 推送失败: blogId={}, authorId={}", blogId, authorId, e);   // A9：失败可观测
    }
}
```

### B1. `RedisIdWorker` 时钟回拨防护（G1；A1 **必须实测**）

**`common/.../utils/RedisIdWorker.java`**

```java
private static final long BEGIN_TIMESTAMP = 1640995200L;
private static final int  COUNT_BITS = 32;
/** 允许的最大时钟回拨秒数；超过则拒绝生成 ID（宁失败不产生可能重复的 ID） */
private static final long MAX_BACKWARD_SECONDS = 5;
private static final DateTimeFormatter DAY = DateTimeFormatter.ofPattern("yyyy-MM-dd");

private final StringRedisTemplate stringRedisTemplate;
private final Clock clock;
/** 上次使用的时间戳；同实例内由 synchronized 保护可见性与原子性 */
private volatile long lastTimestamp = -1L;

public RedisIdWorker(StringRedisTemplate stringRedisTemplate) {
    this(stringRedisTemplate, Clock.systemDefaultZone());
}

/** 测试用：注入可控时间源（SPEC-10 §8.1 要求 mock 时间源） */
RedisIdWorker(StringRedisTemplate stringRedisTemplate, Clock clock) { ... }

public synchronized long nextId(String keyPrefix) {
    LocalDateTime now = LocalDateTime.now(clock);
    long timestamp = now.toEpochSecond(ZoneOffset.UTC) - BEGIN_TIMESTAMP;

    if (timestamp < lastTimestamp) {
        long offset = lastTimestamp - timestamp;
        if (offset > MAX_BACKWARD_SECONDS) {
            throw new IllegalStateException("时钟回拨 " + offset + " 秒，超过阈值，拒绝生成 ID");
        }
        log.warn("检测到时钟回拨 {} 秒，复用上次时间戳", offset);
    } else {
        lastTimestamp = timestamp;
    }
    timestamp = lastTimestamp;                 // 回拨时复用，正常时即自身

    String date = now.format(DAY);             // P5：时区两行保持原样
    long count = stringRedisTemplate.opsForValue().increment("icr:" + keyPrefix + ":" + date);
    return lastTimestamp << COUNT_BITS | count;
}
```

要点：
- **回拨在阈值内复用 `lastTimestamp`**，使 `timestamp` 段不回退，ID 段不重叠；
- **超阈值快速失败**（`IllegalStateException`）而非静默生成可能重复的 ID；
- `synchronized` 保证同实例内 `lastTimestamp` 的可见性；多实例场景下 `count` 由 Redis `INCR`
  保证唯一，且相同 `timestamp` 的实例共享同一 count 空间，本身安全；
- `Clock` 注入使 SPEC-10 §8.1 的"mock 时间源"成为可能（E8 的解法）；生产路径走 1 参构造器，
  行为与现状逐位一致；
- **P5**：`toEpochSecond(ZoneOffset.UTC)` 与本地 `date` 两行保持原样。

## 10. 风险与残留

### 10.1 风险与缓解

| 风险 | 缓解 |
|---|---|
| `docker compose up` 与宿主既有中间件容器端口冲突（3306/6379/8848/9876） | 启动前 `docker ps` 检查；冲突则先停掉旧容器或临时改用其它宿主端口（`${MYSQL_PORT}` 已是环境变量，改端口不影响服务配置） |
| 新增 `ShopFeignClient` 使 `POST /blog` 增加一个远程依赖，shop-service 抖动时发布不可用 | 有意为之（fail-closed，见 A5）。若后续认为可用性优先，可改为"校验失败仅告警"——但那是策略变更，需单独立项 |
| `FollowCacheWarmupRunner` 在 `tb_follow` 很大时拖慢启动 | 本轮量级为演示数据；已 `try/catch` 不阻塞启动。若需支撑大表，改为分页批量 SADD（本轮不做） |
| social-service 首次引入测试基础设施，可能暴露既有代码的可测性缺口 | 已选 Mockito 直测 service（不启 Spring 上下文）；仅 `BlogControllerTest` 用 `@WebMvcTest` 切片，需要 `@MockBean` 掉 Feign 客户端 |
| Feed 异步任务在 JVM 关闭时丢失 | `setWaitForTasksToCompleteOnShutdown(true)` + `awaitTerminationSeconds(30)`；极端情况下丢失的是粉丝收件箱推送（可由后续浏览作者主页补齐），不是订单/资金数据 |

### 10.3 实施中需持续核对的口径

- 每次改动 yaml 后必须 `mvn -o -T 1C -DskipTests compile` 之外，还要抽查至少一个模块的实际启动，
  避免"配置能编译但拉不起来"（Spring 的 `@Value` 默认值会掩盖键名错误——这正是 SPEC-10 §1.2 的教训）。
- `AutoConfiguration.imports` 追加 `RedissonConfig` 后，**必须验证 gateway-service 仍能启动**
  （网关不在 order/agent/rag 之列，不应出现 `RedissonClient` Bean）。
