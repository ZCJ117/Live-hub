# 二级缓存（Caffeine L1 + Redis L2 + 失效广播）设计

> 编制日期：2026-10-09
> 基线：`master@9d31665`
> 需求来源：用户要求"本地缓存 + Redis，完整实现端到端功能"
> 关联：`docs/specs/SPEC-05-缓存正确性缺陷.md`（既有 Redis 单级缓存的契约由它确立）

---

## 1. 背景与现状证据

用户提问"项目到底有没有实现本地缓存 + Redis 的二级缓存"，逐文件核对结论是**没有**：

| 结论 | 证据 |
|------|------|
| 无任何本地缓存实现 | 全仓 Java 源码 `Caffeine` 零命中；`pom.xml` 无 `caffeine`/`guava`/`ehcache` 依赖；无 `CacheConfig`/`CacheManager` Bean；生产代码 `@Cacheable`/`@CacheEvict` 零命中 |
| 现有缓存是**单级 Redis** | `ShopCacheService.getShop`（Redis → DB → 回填）、`ShopTypeServiceImpl.queryList`（同构重复实现） |
| 4 个服务的 `@EnableCaching` 是空转配置 | `OrderApplication`/`VoucherApplication`/`SocialApplication`/`UserApplication`，无任何缓存注解消费它 |
| 文档与代码口径不一致 | `README.md` §1.2「Caffeine本地缓存为预留扩展项」、§10.1 第 5 条「启用Caffeine一级本地缓存」；`docs/specs/README.md` 把「本地缓存（Caffeine）的使用」列为**不核验**的既定事实 |
| 历史上也没有过 | `shop-service` 曾有 `caffeine 3.1.8` 依赖但**全仓零 import**，SPEC-05/11 波次按死代码删除（见 `2026-10-08-spec-05-11-修复-design.md` §1.2）；`common` 的 `CacheClient`（纯 Redis + 逻辑过期、零引用）同批删除 |

### 1.1 必须保留的既有契约（SPEC-05 确立）

- key：`cache:shop:{id}`、`shop:list:`（`RedisConstants` 是唯一事实源，含 `cacheTtlSeconds()` 抖动工厂）
- 值：**实体本体**的 JSON（不是 `Result` 包装对象）
- 正常值 TTL：`1800 + [0,300)` 秒；空值标记：`""` + 60 秒
- 写路径显式失效：`ShopServiceImpl.update`、`ShopController.saveShop`

## 2. 目标与非目标

### 2.1 目标（逐条可验证）

| 编号 | 目标 | 验证方式 |
|------|------|----------|
| G1 | L1 命中时**完全不访问 Redis** | 单测 `verify(redis, never())`；e2e 阶段①（污染 Redis 不改 L1） |

| G5 | L1 命中率可观测 | `CacheStatsLogger` 每 60 秒输出一行 stats |

3. 缓存击穿互斥锁 / 逻辑过期重建（SPEC-05 范围外的既有缺口）；
4. cache-aside 固有的"并发读回填 vs 写失效"竞态修复；
5. Testcontainers 集成测试、Micrometer 指标端点；
6. L1 返回对象的深拷贝；
7. 4 个服务里空转的 `@EnableCaching` 清理（另行处理）。

## 3. 决策记录（已与用户逐条确认）

| 编号 | 决策 | 理由 |
|------|------|------|
| D1 | L1 用 **Caffeine**；跨实例失效用 **Redis Pub/Sub 广播** | 保留现有 Redis key/值格式与契约测试，`ShopCacheService` 改动面最小 |
| D2 | 组件放 `common`，但**本期只接商铺两处**（商铺实体、商铺分类列表） | 收益立即可量，其他服务零改动 |
| D3 | L1 参数：`maximumSize=1000`、`expireAfterWrite=10s`、`recordStats=true` | 广播是主失效手段，10s 只是广播丢失/断线时的兜底窗口 |
| D4 | 广播载体：**Spring Data Redis Pub/Sub**（`RedisMessageListenerContainer`） | common 已有 `spring-boot-starter-data-redis`，不引入第二个客户端体系；at-most-once 由 D3 兜底 |
| D5 | 验收：单测（真 Caffeine + mock Redis）+ **真两实例 + 真 Redis 的 e2e 脚本** | 跨实例失效在单测里只能 mock，必须行为级验证 |
| D6 | 组件把 Redis 异常**降级为未命中 + warn**，不上抛 | 统一到 `ShopTypeServiceImpl` 更稳的口径；缓存故障不应让业务 500 |
| D7 | `hmdp.cache.enabled` 默认 **false**，仅 shop-service 显式开启 | 组件在 common，但不能给其他 7 个服务塞进无用订阅连接；漏开会 fail-fast |

## 4. 架构与组件

```
shop-service                                  common（自动配置，按开关装配）
┌────────────────────────┐                  ┌──────────────────────────────────────┐
│ ShopServiceImpl.update │                  │ MultiLevelCache<V>                    │
│ ShopController.saveShop│──evict──┐        │   L1 Caffeine(1000, 10s, recordStats) │
│ ShopServiceImpl.queryById ─┐      │        │   L2 StringRedisTemplate(JSON)         │
│ ShopCacheService      ─────┤      │        │   get(key, loader) / evict(key)        │
│ ShopTypeServiceImpl.queryList ─────┴───────►│                                       │
└────────────────────────┘                  │ MultiLevelCacheFactory                 │
                                            │ LocalCacheRegistry   （实例注册表）     │
                                            │ CacheInvalidationPublisher（发布）      │
                                            │ CacheInvalidationSubscriber（订阅）     │
                                            │ CacheStatsLogger（60s 打命中率）        │
                                            └──────────────────────────────────────┘
```

### 4.1 关键设计：key 即 Redis 全键

`MultiLevelCache` 的 key 直接使用 Redis 全键（`cache:shop:12`、`shop:list:`），L1 与 L2 共用同一键空间。收益：

- `RedisConstants` 的"key 唯一事实源"纪律不动，契约测试与 `.e2e` 里 `redis-cli GET` 的核对方式不动；
- 广播消息只需携带一个字符串 key，无需引入 `{cache, key}` 结构；
- 订阅端对所有已注册 L1 统一执行 `invalidate(key)`，key 不匹配时 Caffeine 天然 no-op，省掉"消息该投给哪个 L1"的路由逻辑。

### 4.2 组件接口

```java
package com.hmdp.cache;

/** L1(Caffeine) + L2(Redis) 二级缓存；key 即 Redis 全键 */
public class MultiLevelCache<V> {
    /** L1 → L2 → loader → 回填 L2+L1；loader 返回 null → 写 60s 空值标记且不写 L1 */
    public V get(String key, Supplier<V> loader);
    /** 写路径失效：① Redis DEL ② 本实例 L1 invalidate ③ 广播（顺序理由见 §6） */
    public void evict(String key);
    public CacheStats stats();
    public String name();
}

public class MultiLevelCacheFactory {
    public <V> MultiLevelCache<V> create(String name, Type valueType);
}
```

- 值类型用 `java.lang.reflect.Type`：`Shop.class` 直接可用；`List<ShopType>` 用 `new TypeReference<List<ShopType>>(){}.getType()`。（已核对 hutool 5.8.22 的 `JSONUtil.toBean(String, java.lang.reflect.Type, boolean)` 存在。）
- 空值标记与 TTL 抖动**复用既有常量** `CACHE_NULL_TTL` / `cacheTtlSeconds()`，不另发明策略。
- 新增常量：`RedisConstants.CACHE_INVALIDATE_CHANNEL = "cache:invalidate"`。
- 依赖：`com.github.ben-manes.caffeine:caffeine:3.1.8`（根 `pom.xml` 手工加 `<caffeine.version>`，本项目未导入 spring-boot BOM；该版本已在本地 m2，可离线构建）。

### 4.3 广播装配

```java
// common：仅当 hmdp.cache.enabled=true 时装配
@Bean RedisMessageListenerContainer cacheInvalidationListenerContainer(
        RedisConnectionFactory cf, LocalCacheRegistry registry) {
    RedisMessageListenerContainer container = new RedisMessageListenerContainer();
    container.setConnectionFactory(cf);
    container.addMessageListener(new CacheInvalidationListener(registry),
            new ChannelTopic(RedisConstants.CACHE_INVALIDATE_CHANNEL));
    return container;
}
```

订阅端单独成为可单测的类 `CacheInvalidationListener implements MessageListener`，`onMessage` 只做一件事：把消息体交给注册表。

`LocalCacheRegistry` 持有 `CopyOnWriteArrayList<MultiLevelCache<?>>`，由 `MultiLevelCacheFactory.create(...)` 在创建后登记（不是构造器里自注册——避免构造期泄漏 `this`）；`evictLocal(key)` 只清 L1，**不**删 Redis、**不**再广播，异常按缓存逐个兜住（不外逸到 Redis 监听容器，因此容器侧无需再包一层 try/catch）。

`CacheStatsLogger` 用守护线程 `ScheduledExecutorService`（沿用 `ShopCacheWarmUp` 的既有范式）每 60 秒对 registry 内每个 cache 输出：`name / size / hitRate / hitCount / missCount / evictCount`。

## 5. 数据流

### 5.1 读（`ShopCacheService.getShop` / `ShopTypeServiceImpl.queryList`）

1. **L1 命中** → 直接返回（不碰 Redis —— L1 的全部收益在此）；
2. L1 miss → L2 GET → 有值 → 反序列化 → 写 L1 → 返回；
3. L2 命中空值标记（`""`）→ 返回 null，且**不写 L1**；
4. L2 miss → `loader` 查 DB → 返回 null/空 → 写 60s 空值标记 → 返回 null；
5. `loader` 返回非空 → 写 L2（`1800+jitter`）→ 写 L1 → 返回。

### 5.2 写（`ShopServiceImpl.update` / `ShopController.saveShop`）

`DB 落库` → `cache.evict(key)` → `[Redis DEL → 本实例 L1 invalidate → publish]`。

### 5.3 分类列表的空列表语义

`ShopTypeServiceImpl.queryList` 的 `loader` 在 DB 返回空列表时返回 `null`，由组件写空值标记；调用方按 `null → Result.fail("列表信息不存在")` 处理，保持现有对外语义与日志不变。

## 6. 失效一致性与删除顺序

1. **订阅端只清 L1，不回环**：收到消息不删 Redis、不再广播，与 `MultiLevelCache.evict` 的完整失效区分开。
2. **删除顺序：Redis DEL → L1 invalidate → publish**。若先删 L1 再删 Redis，中间窗口的并发读会 miss L1、读到尚未删除的旧 Redis 值，并把旧值回灌 L1，等于给脏值"续命"到 L1 TTL。按此顺序，最坏情况只是本实例极短暂地读旧 L1，且被 10s TTL 封顶。
3. **广播是 at-most-once**：Redis Pub/Sub 无重投、无持久化，订阅端断线期间的消息永久丢失 —— 该窗口的脏读由 L1 TTL（10 秒）封顶，这是 D3 存在的原因。
4. **既有竞态不在本次范围**：并发读回填与写失效的竞态在当前纯 Redis 单级缓存中已存在，L1 不放大它（L1 最坏 10s ≪ L2 最坏 30min）。

## 7. 错误处理与降级

| 场景 | 行为 |
|------|------|
| Redis GET/SET 异常 | 降级为"未命中" + `warn` 日志，继续回源 DB；**不上抛**。L1 命中路径不受影响 |
| 空值标记写入失败 | 记 `warn`，仍返回 null |
| 广播发布失败 | 记 `warn`，业务正常返回（DB 已提交），靠 L1 10s 兜底 |
| 订阅端处理异常 | 逐个缓存 try/catch 记 `error`（在 `LocalCacheRegistry.evictLocal` 内），异常不外逸到 Redis 监听容器 |
| L2 值反序列化失败 | 记 `warn`，按"未命中"处理并**回源 DB**（不把 null 当结果返回、也不写空值标记） |
| `loader`（DB）异常 | 正常向上抛，不吞 |

> 这是相对现状的**行为收窄**：`ShopCacheService` 当前会让 Redis 异常上抛成 500，`ShopTypeServiceImpl` 已经是降级口径。本设计统一到后者。现有 10 个缓存用例中没有断言异常传播的用例，改动不破坏它们。

## 9. 测试与验收

### 9.1 单测（common 新增 `MultiLevelCacheTest`：真 Caffeine 实例 + mock `StringRedisTemplate`）

| 编号 | 用例 | 断言要点 |
|------|------|----------|
| U1 | L1 命中 | 第二次 `get` 不再调用 `opsForValue().get` |
| U2 | L1 miss → L2 命中 | 回填 L1；第三次调用仍不读 Redis |
| U3 | L1/L2 均 miss | `loader` 恰好调用 1 次；写 L2 的 TTL ∈ [1800, 2100) |
| U4 | loader 返回 null | 写 `""` + TTL ≤ 60s；**不写 L1**；再次 `get` 不调 loader |
| U5 | `evict` | L1 已移除 + `redis.delete` 调用 1 次 + `publisher.publish` 调用 1 次 |
| U6 | 收到广播 | 只清 L1：`redis.delete` **零**交互、`publish` **零**交互 |
| U7 | 发布失败 | publish 抛异常 → `evict` 不抛、Redis 删除已完成 |
| U8 | Redis GET 异常 | 不抛，降级回源 DB 并返回结果 |
| U9 | stats | hit/miss 计数与命中率正确（`getIfPresent` 语义：命中 1 次、未命中 1 次 ⇒ hitRate=0.5） |
| U10 | L1 容量上限 | 写入 100 个不同 key（配置上限 10）后**先触发一次读**再断言 `estimatedSize()` ≤ 10 |
| U11 | L1 兜底 TTL | 配置 TTL=150ms，写入后等 300ms 再读 ⇒ 必须回源 |
| U12 | 广播发布失败 / Redis 读写异常 / 反序列化失败 | 三条降级路径各一例（§7 表逐行对应） |

**两条实测约束（编写实施计划时在本机 Caffeine 3.1.8 + hutool 5.8.22 上真跑得出，用例必须遵守）**：

1. Caffeine 的按容量淘汰是**异步维护**的：`maximumSize(10)` 写入 100 条后 `estimatedSize()` 仍报 100，需一次后续访问才降到 10 → U10 必须先读一次再断言，否则用例必然失败。
2. hutool 对 **record** 的 JSON 序列化结果是 `{}`，`JSONUtil.toBean(json, Type, false)` 对 record 抛 `ConvertException` → 用例一律用项目实体（`Shop`/`ShopType`）这类 getter/setter POJO，**不要用 record 当测试替身**。

**已知未覆盖项（如实记录）**：真实 `RedisMessageListenerContainer` 的订阅行为**不在**切片测试覆盖范围内（切片测试为避免异步连接噪音，预置了 mock 容器以跳过真实 Bean，只验证条件开关与四个组件 Bean）。真实订阅链路由 §9.3 阶段②的行为断言负责——这是本设计对"广播真的收到了"的唯一证据来源。

### 9.2 单测（shop-service 既有用例）

- `ShopCacheServiceTest`（6 例）、`ShopTypeServiceImplTest`（4 例）：**断言全部保留**，只改 `setUp` 的构造方式（在 mock 的 `StringRedisTemplate` 上构造 `MultiLevelCacheFactory`，并注入 mock `CacheInvalidationPublisher`）。每个测试方法使用新建的 Factory ⇒ L1 为空 ⇒ 读路径仍落到 mock 的 Redis 交互上。
- 实施时以真实测试输出为准：若某个用例断言了会被 L1 短路掉的 Redis 交互，则按行为变化更新该断言并在提交信息中说明原因（不静默改断言）。
- 新增 3 例：L1 命中后 `verify(get)` 只调 1 次；`evict` 后本实例立即回源；广播回调不删 Redis。

### 9.3 端到端（`.e2e/vrun/spec-12-multilevel-cache.sh`，真两实例 + 真 Redis）

前置：Nacos/MySQL/Redis 已起（配方见既往 e2e 环境笔记）。启两个**新建**的 shop-service 实例：`--server.port=8089`（写端 A）与 `--server.port=8090`（读端 B），共用同一 Redis 与 DB，Sa-Token 会话经 Redis 共享故同一 token 对两实例均有效。

> 端口选择依据：`8081`~`8088` 已被 8 个服务占用（`8083` 是 **voucher-service**，不是空闲端口），`8091` 是 Seata、`8848` 是 Nacos，故取 `8089`/`8090`。既有 e2e 脚本 `.e2e/vrun/spec-06-07-09-e2e.sh` 顶部的端口表可复核。

三项执行约束：

1. **必须直连实例端口**（不经网关）——只有直连才能指定"读/写发生在哪个实例上"；这与"禁止绕过网关注册"的部署约定不冲突：本例是为了验证实例内 L1 的跨实例失效，token 仍由服务内 Sa-Token 校验。
2. `PUT /shop` 带 `@SaCheckRole("admin")`，需 admin 角色 token（`hmdp.admin-user-ids` 白名单，可沿用 `.e2e/vrun` 既有签发方式）。
3. **时序约束**：L1 TTL 仅 10 秒，阶段①的三步（B 首读 → 污染 Redis → B 再读）必须在 10 秒内完成，否则 L1 自然过期会让阶段① 失去判别力。脚本中对此加显式耗时断言。

| 阶段 | 动作 | 断言（防假绿设计） |
|------|------|--------------------|
| ① 证明 L1 真生效 | B 读 `/shop/{id}` 得 v0 → `redis-cli SET cache:shop:{id} '<伪造值 vX>'`（**不发广播**）→ 立刻再读 B | B 仍返回 v0。若返回 vX 说明 L1 未生效，此时阶段②的通过毫无判别力 |
| ② 证明广播失效 | `redis-cli DEL cache:shop:{id}` → 经 A `PUT /shop` 改名 v1 → **2 秒内**读 B | B 返回 v1。因为 L1 里是 v0（阶段①已证明）、10s TTL 未到，返回 v1 只可能来自广播失效 |
| ③ 证明 L2 同步 | `redis-cli GET cache:shop:{id}`；另 grep B 实例日志的 `CacheStatsLogger` 行 | 为空或 v1；日志出现命中率行（辅助证据） |

脚本结束必须杀掉 8083 实例，避免污染其他 e2e 用例。
