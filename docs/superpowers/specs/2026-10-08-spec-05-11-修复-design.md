## 1. 背景

`docs/specs/` 下的 11 份 SPEC 是 2026-10-07 对全仓的系统性缺陷审计。SPEC-01/02 与 SPEC-03/06/07 已交付。本设计覆盖下一批两份：

### 1.1 缺陷复核结论

两份 SPEC 编制于 `master@3c9a6e2`，此后 SPEC-03/06/07 已落地。动手前逐条复核，**发现 4 处 SPEC 正文已过期或自相矛盾**（详见 §3），其余条目全部仍然成立：

- `queryById` 的 `unless = "#result == null"` 对 `Result.fail(...)` 恒为 false → 失败 Result 被缓存 30 分钟（`ShopServiceImpl:360`，`CacheConfig:48`）；

- `warmUpPopularShops` 调 `this.queryById(...)` 是类内自调用，绕过 AOP → 预热不落缓存（`ShopServiceImpl:143`）；
- `CacheClient.queryWithMutex` 的 `finally` 在未持锁时也 `unlock`，且 `unlock` 不校验持有者（`CacheClient:219-243, 195-197`）；`CacheClient` / `SimpleRedisLock` 外部引用数均为 **0**；
- `SystemConstants.IMAGE_UPLOAD_DIR` 为硬编码本机路径且零引用（`SystemConstants:4`）；
- 仓库根 `api-endpoints.txt`（54 KB 的 ACP 项目 API 清单）、`openapi.json`（2.3 MB，`servers[0].url=localhost:18088`）与本项目零交集。

## 4. Workstream A — SPEC-05 缓存正确性

### A1. 新组件 `ShopCacheService`（新建）

`shop-service/src/main/java/com/hmdp/shop/service/ShopCacheService.java`

职责单一：**商铺实体的读路径与失效**。注入 `StringRedisTemplate` + `ShopMapper`；**不注入 `IShopService`**，以避开与 `ShopServiceImpl` 的循环依赖（`ShopServiceImpl extends ServiceImpl<ShopMapper, Shop>`，若彼此注入会形成构造环）。

```
getShop(Long id):
    key = CACHE_SHOP_KEY + id
    json = stringRedisTemplate.opsForValue().get(key)

    1. StrUtil.isNotBlank(json)  → JSONUtil.toBean(json, Shop.class)          返回
    2. json != null（空值标记）   → 返回 null（防穿透，不触库）                 返回
    3. 未命中                     → shopMapper.selectById(id)
         ├ null  → SET key "" EX CACHE_NULL_TTL 秒；返回 null
         └ 有值  → SET key json EX (CACHE_TTL_BASE_SECONDS + ThreadLocalRandom
                                   .current().nextInt(CACHE_TTL_JITTER_SECONDS)) 秒
                   返回 shop

evict(Long id):
    stringRedisTemplate.delete(CACHE_SHOP_KEY + id)
```

要点：

- **缓存 `Shop` 本体而非 `Result`**（G1 的根因，SPEC-05 §1.7）。`Result` 包装对象不再进入缓存，失败分支因此不可能被缓存。
- **空值 60 秒短 TTL**（G5、A1）。正常值 TTL 与之分离，这是 `@Cacheable` 无法表达的部分。
- **TTL 抖动**（G7、A8）：`1800 + [0,300)` 秒。
- 无 L1 本地缓存（用户裁定）。理由：A1–A11 无一条要求 L1；G3 仅靠 L2 即可成立；多实例下进程内 L1 会带来"其他实例 30~60 秒返回旧值"的一致性问题。SPEC-05 §5.1 对该问题自身也持保留（"若 L1 是进程内缓存……"）。

### A2. `RedisConstants` 的缓存常量

```java
public static final String CACHE_SHOP_KEY = "cache:shop:";   // 保留（SPEC-05 读路径使用）
/** 空值标记 TTL，单位：秒（SPEC-05 §5.1：把负缓存窗口从 30 分钟压到 60 秒） */
public static final Long    CACHE_NULL_TTL = 60L;            // 2L(分钟) → 60L(秒)
/** 缓存基础 TTL，单位：秒（商铺与商铺分类共用） */
public static final Long    CACHE_TTL_BASE_SECONDS = 1800L;
/** 缓存 TTL 抖动上限，单位：秒；实际 TTL = 基础值 + [0, 抖动) */
public static final Integer CACHE_TTL_JITTER_SECONDS = 300;
```

作为 G7 要求的"常量提供方"：`ShopCacheService`（商铺）与 `ShopTypeServiceImpl`（分类列表）共用同一组基础值/抖动，杜绝"改了一处、另一处仍是固定值"。两处写入点的 TTL 表达式统一为：

```java
CACHE_TTL_BASE_SECONDS + ThreadLocalRandom.current().nextInt(CACHE_TTL_JITTER_SECONDS)
```

> 新常量刻意不取名 `CACHE_SHOP_TTL*`，以免污染 SPEC-11 §8.1 中 `CACHE_SHOP_TTL` 的 grep 断言（该断言在 §3-D4 中保留其原意）。

### A4. 预热重构（G2、G3）

删除 `ShopServiceImpl` 中的预热族（`warmUpCacheOnStartup` / `warmUpPopularShops` / `warmUpShopsByType` / `warmUpGeoData` / `warmUpCache` / `warmUpShopCache` / `getCacheWarmupStatus` / `init` / `destroy` / `cacheWarmupExecutor`），替换为两个独立组件：

**`ShopCacheWarmUp implements ApplicationRunner`**（新建）

- `run(ApplicationArguments)` 只做 `executor.submit(this::warmUpPopularShops)` 后**立即返回** —— 用 `ApplicationRunner` 而非 `@PostConstruct`：容器就绪后执行，不占启动关键路径（G2）。
- 预热体：`shopMapper.selectList(new QueryWrapper<Shop>().orderByDesc("score").last("LIMIT 50"))`（`tb_shop.score` 确实存在，`docs/SQL/start.sql:76`）→ 逐个 `shopCacheService.getShop(id)`。
- **必须经 `ShopCacheService` bean 调用**，取代原 `this.queryById(...)` 自调用——这是 G3 成立的唯一原因。
- 删除 `Thread.sleep(10000)`。
- 顺手修正原注释 `// 假设有评分字段`（字段真实存在，属"注释与实现不符"）。

**`ShopGeoIndexWarmUp implements ApplicationRunner`**（新建）

- 同样异步入队，不阻塞启动。
- 保留原 GEO 写入逻辑（`opsForGeo().add(SHOP_GEO_KEY + typeId, locations)`），注释明确"GEO 索引预热，与 shopCache 无关"（SPEC-05 §5.2 第 4 条的后半句）。
- 原 `this.query().isNotNull("x").isNotNull("y").list()` 的全表扫描改为按 `Page<>(n, 500)` **分块**拉取（§5.2 第 5 条），避免启动阶段一次性把整表读入内存。

两个 `ApplicationRunner` 各自持有一个单线程 daemon `ExecutorService`（不引入共享的执行器 bean），`@PreDestroy` 时 `shutdownNow`（沿用原 `destroy()` 的销毁语义）。

> **原 `warmUpCache()` / `warmUpShopCache(List<Long>)` / `getCacheWarmupStatus()` 一并删除**，连同 `IShopService` 中的三处声明。它们经全仓 grep 确认**零调用方**（无 Controller 暴露、无 Feign 引用、无测试引用），且其实现体调用的正是被拆掉的私有预热方法——保留将无法编译。此项不在 SPEC-11 §1.2 的清单内，属按 G2"不含零引用方法"精神补齐（已获用户裁定）。

### A7. `@Min(1)` 的运行时支撑（A7 可达性的必要条件）

当前 shop-service **没有** `jakarta.validation` API 与 hibernate-validator：`@Min` 会静默失效。且 Bean Validation 在**方法参数**上触发的是 `ConstraintViolationException`，而 Spring Boot 默认将其映射为 **500**——两条路都到不了 A7 要求的 400。因此：

1. `shop-service/pom.xml` 增加 `spring-boot-starter-validation`（compile）。agent-service 已在用同一依赖，本地仓库已有，离线可解。
2. 新建 `shop-service/src/main/java/com/hmdp/shop/config/ShopValidationExceptionHandler.java`：

```java
@RestControllerAdvice
@Slf4j
public class ShopValidationExceptionHandler {
    @ExceptionHandler(ConstraintViolationException.class)
    public ResponseEntity<Result> handleConstraintViolation(ConstraintViolationException e) {
        String msg = e.getConstraintViolations().stream()
                .map(ConstraintViolation::getMessage).findFirst().orElse("请求参数不合法");
        return ResponseEntity.badRequest().body(Result.fail(msg));
    }
}
```

放在 `com.hmdp.shop.config` 包内，确保被 `@SpringBootApplication`（扫描根 `com.hmdp.shop`）拾取。**不收拢为全局 catch-all**，仅处理约束违例，避免把真实缺陷吞成 400。

> 注：`SaTokenConfig` 对 `/**` 强制登录且 `/shop/**` 不在白名单，因此真实调用需先通过鉴权才可能观察 400。这不改变 A7 的语义（"分页参数越界返回 400 而非 500"），只影响测试的构造方式（§7.1）。

|------|------|
| `shop-service/.../config/CacheConfig.java` | 其 `CacheManager` bean 改造后无任何消费者 |
| `ShopApplication` 的 `@EnableCaching` | 无缓存注解可驱动 |
