## 1. 产品概述

### 1.1 产品背景

hm-dianping 平台当前的用户客服路径完全依赖人工与页面自助：用户遇到"秒杀订单未到账""优惠券无法使用""商户服务投诉"等问题时，只能自行翻找订单页或通过无结构化的留言反馈，响应时效无保障、平台侧无工单沉淀。

与此同时，平台已完成两项关键能力建设：

1. **完整的微服务业务闭环**：order/voucher/shop/social 四个业务服务的 REST API 可覆盖客服场景 90% 以上的事实查询需求；
2. **已上线的 rag-service（8087）**：具备 PgVector 向量检索 + tsvector 全文检索 + RRF 融合、GLM-5 流式生成（SSE）、会话管理等 AI 基础设施。

市场侧，2025 年中国 AI Agent 市场规模 182.34 亿元、同比增长 78%（《报告》确认事实），"智能客服 + 工单流转"是大厂已量产验证（阿里小蜜、京东京小智、美团智能客服）、且天然适配 IM 对话形态的 Agent 落地场景。本项目选取该场景，将现有微服务 API 工具化（Function Calling），构建"**对话式自助 → 工具调用查证 → 关键操作人工确认 → 疑难自动建单路由**"的端到端智能客服产品。

### 1.2 产品目标

| 维度 | 目标 | 衡量方式 |
|---|---|---|
| 业务目标 | 客服人工咨询量下降 40% 以上；疑难问题 100% 建单可追溯 | 转人工率、工单覆盖率 |
| 体验目标 | 一次会话解决率（无需转人工、无需二次来访）≥ 70%；问题响应从"小时级"到"秒级" | 会话级埋点 |
| 技术目标 | 建成可复用的 Agent 工程底座：工具调用、ReAct 编排、记忆机制、人机协同、审计与降级 | agent-service 上线并通过压测 |

### 1.3 用户价值

- **C 端用户**：用一句自然语言直接获得"查得到、办得了、有下文"的服务——订单状态实时查证（非模型编造）、退款一键申请（确认后提交）、投诉自动建单（有工单号可追）。
- **平台人工客服**：Agent 处理高频标准问题，人工聚焦疑难；转人工时自带对话摘要与上下文，接手成本降低。
- **平台运营**：全量会话与工单数据沉淀，形成问题热力图（哪个商户/哪类券/哪个环节出问题最多），反哺商户治理与产品迭代。

### 1.4 市场定位

本项目为**求职作品集与工程能力验证型产品**，产品形态对标大厂智能客服（阿里小蜜/京东京小智）的核心链路子集：

- **定位语**：面向本地生活平台的"会做事"的客服 Agent——不止回答，还能查证、代办、建单。
- **差异化主张**：答案基于工具调用的事实查证（可溯源），关键写操作强制人机协同确认，全程审计可回放。
- **非商业化阶段**：不涉及对外收费；但工程上预留计量口径（会话成本、Token 消耗），为商业化叙事提供数据支撑。

### 1.5 产品范围与非目标（Non-goals）

**范围**：平台内嵌 IM 式客服会话（Web/H5），覆盖订单咨询、券咨询、商户信息、退款申请、投诉建单、转人工六大意图，含客服工单工作台（P2）。

**明确不做**：

1. 不做外呼/邮件/微信生态等站外渠道接入；
2. 不做多租户与对外开放 API；
3. 不做语音客服与数字人；
4. 不做基于用户行为的主动营销推送；
5. 不自研/微调模型，模型层仅通过 OpenAI 协议兼容接口调用 GLM-5 / glm-4-flash，保持可替换。

## 2. 用户画像与典型使用场景

### 2.1 用户画像

**画像 A：着急的普通用户（主用户，占比 ~70%）**

- 25-35 岁，移动端为主；刚参加完秒杀，券订单状态异常，情绪着急、耐心低（等待超过 10 秒即可能放弃）。
- 核心诉求：**快速知道"我的单子怎么了"**，期望 3 轮对话内解决。
- 关键设计含义：首响应必须快（P90 首 token ≤ 1.5s）、查单结果必须结构化可扫读、失败时必须有明确下一步（工单号/转人工）。

**画像 B：谨慎的中年用户（占比 ~20%）**

- 36-50 岁，打字慢、描述模糊（"我买的东西没了"），对 AI 自动执行操作警惕。
- 核心诉求：**退款/投诉有人兜底**，希望"机器办事、人工把关"。
- 关键设计含义：澄清追问能力、确认卡片文案直白（写明将执行什么操作、影响什么）、随时可转人工且入口显著。

**画像 C：平台人工客服（内部用户）**

- 承接 Agent 转人工的会话与工单；关注接手时上下文是否完整、工单分类是否准确。
- 关键设计含义：转人工必须附 LLM 摘要 + 关键事实（订单号/券号）；工单带自动分类与优先级，减少人工分拣。

### 2.2 典型使用场景

**场景 1：秒杀订单未到账（P0 核心路径）**

> 用户："我上周抢的券怎么还没到？" → Agent 调用 `query_my_orders` 拉取近 7 天订单 → 以卡片列出订单（券名/金额/状态/时间）→ 用户追问"那这个未支付的是什么" → Agent 解释状态含义并给出支付入口指引。

**场景 2：退款申请（P0 人机协同路径）**

> 用户："这个券我不要了，退款。" → Agent 定位订单 → 确认归属后生成退款申请卡片（订单详情 + 原因输入框 + 确认/取消按钮）→ 用户点击确认 → 后端二次校验后提交，返回受理编号 → 同步创建工单供人工复核。

**场景 3：优惠券使用咨询（P0）**

> 用户："满 100 减 30 的券为什么用不了？" → Agent 调用 `query_voucher` 取券规则（适用店铺/品类/有效期/使用门槛）→ 结合订单上下文定位原因（如"该券不适用于 alcoholic 品类"）→ 给出可用的解决路径。

**场景 4：商户投诉（P0 建单路径）**

> 用户："这家店服务态度太差了，我要投诉。" → Agent 先安抚并结构化收集要素（店铺名/发生时间/问题类型）→ 调用 `create_ticket`（category=商户服务，priority=中，附对话摘要）→ 返回工单号与预计处理时效 → 用户可随时凭工单号查询进度。

**场景 5：转人工兜底（P0）**

> 连续 2 次工具调用失败，或用户输入"转人工/我要投诉你们机器人" → Agent 停止生成，推送转人工卡片（含摘要预览）→ 人工客服接入后看到完整上下文。

### 3.1 FR-01 客服入口与会话建立

- **用户故事**：作为用户，我希望在 App 任意页面通过"联系客服"入口一键进入对话，以便立刻描述我的问题。
- **优先级**：P0
- **交互流程**：
  1. 用户点击「我的 → 联系客服」（或订单/券详情页「遇到问题」快捷入口）；
  2. 前端 `POST /agent/chat` 建立 SSE 连接，服务端创建 `agent_session`（状态 ACTIVE），返回 `sessionId` 与欢迎语（流式输出）；
  3. 欢迎语包含能力提示：「我可以帮您查询订单、咨询优惠券、申请退款、提交投诉」；
  4. 若用户从订单/券详情页进入，入口携带 `context={orderId|voucherId|shopId}` 预注入会话（用户首句即可说"就是这个单子"）。
- **边界条件**：
  - 未登录用户点击入口 → 引导登录（客服会话强制实名，防止匿名滥用）；
  - SSE 建连失败/超时（3s）→ 前端降级为轮询模式提示"当前使用慢速通道"，并重试 1 次；
  - 同一用户并发会话数 > 1 → 新会话建立前提示"已有进行中的会话，是否继续"，选择继续则复用未过期会话；
  - 会话空闲 30 分钟 → 服务端自动置 CLOSED 并推送结束语。
- **验收标准**：
  1. 登录态下从任一入口进入，2s 内出现欢迎语首字；
  2. 带订单上下文进入后，首句"这个单子怎么退款了"能正确关联该订单（集成测试用例覆盖）；
  3. 断网重连后（5 分钟内）会话上下文不丢失。

### 3.2 FR-02 多轮对话与上下文管理

- **用户故事**：作为用户，我希望 Agent 记住我前几句话说过的事（比如我已经报过的订单号），以便不用重复描述。
- **优先级**：P0
- **交互流程**：
  1. 用户发送消息 → 前端本地立即渲染（气泡 + "发送中"状态）；
  2. 服务端组装上下文：system prompt + 长期记忆（P2，可选）+ 短期记忆（Redis 中最近 10 轮）+ 当前消息；
  3. 超过 10 轮时触发 LLM 摘要压缩（历史 → 512 字摘要），摘要存 `agent_session.summary`；
  4. 生成完成后更新 Redis 历史，重置 TTL。
- **边界条件**：
  - 单条消息长度 > 500 字 → 截断并提示用户精简（工具调用场景长文本无意义）；
  - 发送频率 > 5 条/10 秒 → 触发频控（见 FR-11），返回友好提示；
  - 摘要压缩失败 → 降级为"仅保留最近 6 轮"，不阻塞对话；
  - 用户发送空消息/纯表情 → 返回引导话术，不进入 LLM。
- **验收标准**：
  1. 10 轮以内的指代消解正确率 ≥ 90%（测试集：50 组多轮用例，如第 1 轮报订单号、第 5 轮说"就刚才那个"）；
  2. 第 11 轮起摘要生效，单请求 prompt Token 不超过 4K（日志抽查）；
  3. 会话关闭后 Redis key 过期，无内存泄漏（压测后 Redis 内存回归基线）。

### 3.3 FR-03 意图识别与路由

- **用户故事**：作为用户，无论我怎么表达（口语化、模糊、带情绪），我希望 Agent 都能理解我要办的事，并走对处理路径。
- **优先级**：P0
- **交互流程**（Planner 内部流程，对用户透明）：

```
用户消息 → 意图分类（LLM，输出 JSON：{intent, entities, confidence}）
  intent ∈ {ORDER_QUERY, VOUCHER_CONSULT, SHOP_CONSULT, REFUND, COMPLAINT, CHAT, HUMAN_DEMAND}
  ├─ 查询类（ORDER/VOUCHER/SHOP）→ 进入 ReAct 工具调用循环
  ├─ REFUND → 工具调用查证 + 生成确认卡片（FR-08）
  ├─ COMPLAINT → 要素收集 + 建单（FR-09）
  ├─ CHAT（寒暄/闲聊/超范围）→ 免工具直接生成，超范围话题礼貌引导回客服范围
  └─ HUMAN_DEMAND（明确要求人工）→ 直接走转人工（FR-10）
```

- **边界条件**：
  - confidence < 0.6 → 输出澄清话术（"您是想查询订单还是咨询优惠券的使用？"），最多连续澄清 2 轮，第 3 轮降级为菜单选择（按钮：查订单 / 查券 / 退款 / 投诉 / 转人工）；
  - 复合意图（"查下我的单子，顺便把这个退了"）→ 拆解为有序子任务依次执行，工具调用上限 8 步；
  - 意图与上下文冲突（会话在退款流程中用户突然问商户问题）→ 中断当前流程、回答新问题，并提示"您的退款申请尚未提交"。
- **验收标准**：
  1. 意图分类准确率 ≥ 95%（标注测试集 200 条，覆盖口语化/错别字/方言表达）；
  2. 澄清轮次均值 ≤ 1.2 轮（埋点统计）；
  3. 超范围话题（闲聊天气、写作文请求）100% 被引导回客服范围，无越界回答（安全测试用例 30 条全过）。

### 3.4 FR-04 工具调用过程可视化

- **用户故事**：作为用户，我希望看到 Agent"正在查询我的订单"的过程，以便信任答案不是瞎编的。
- **优先级**：P0
- **交互流程**：
  1. Agent 发起工具调用时，SSE 推送 `tool_call` 事件（含友好文案："正在为您查询订单…"）；
  2. 调用完成推送 `tool_result` 事件（含结果摘要："已找到 3 条订单记录"）；前端渲染为可折叠的状态条（默认收起，展开可见参数与结果 JSON）；
  3. 调用失败推送失败态文案，并进入 FR-10 的失败判断逻辑。
- **边界条件**：
  - 展开态仅在本端展示，不进入会话历史回放（避免历史记录噪音）；
  - 同一会话连续工具调用 ≥ 4 次 → 状态条合并显示"已进行 4 步查询"；
  - 工具返回数据含敏感字段（手机号、他人昵称）→ 结果摘要中脱敏（138****1234）。
- **验收标准**：
  1. 每次工具调用前端可见状态条，从 `tool_call` 到 `tool_result` 的 UI 反馈间隔 ≤ 100ms；
  2. 工具结果摘要中的敏感字段脱敏率 100%（安全测试用例覆盖）；
  3. 状态条文案与实际调用的工具语义一致（抽查 50 次无错位）。

### 3.5 FR-05 订单查询

- **用户故事**：作为用户，我希望直接问"我上周秒杀的券订单怎么还没到"，就能看到真实订单状态，而不是自己翻页面。
- **优先级**：P0
- **交互流程**：
  1. 意图识别为 ORDER_QUERY → Planner 决定调用 `query_my_orders(orderId?, status?, timeRange?)`（Feign → order-service）；
  2. 结果为多条时，LLM 生成结构化订单卡片列表（券名/金额/状态徽标/下单时间），按时间倒序，默认最多展示 5 条 + "查看更多"；
  3. 结果为空 → 话术引导（"未找到您近 7 天的订单，是否需要扩大时间范围？"），用户确认后扩大到 30 天；
  4. 用户点选某订单 → 后续对话自动聚焦该订单。
- **边界条件**：
  - 用户提供的订单号不属于本人 → 明确拒绝："该订单不存在或非您本人的订单"（鉴权：工具层强制注入 userId 过滤，禁止 LLM 传他人 ID 查询）；
  - 订单数 > 50 → 强制分页（每页 5 条），不一次性渲染；
  - order-service 超时（2s）/熔断 → 返回"订单服务暂时繁忙"，并自动重试 1 次；仍失败 → 主动建议建单或转人工；
  - 订单状态为已取消 → 卡片置灰并注明取消原因（若有）。
- **验收标准**：
  1. 查询结果与 order-service 数据库直查结果 100% 一致（自动化对拍测试 100 条）；
  2. 越权查询（构造他人订单号）100% 被拦截，且响应中不泄露订单存在性；
  3. 服务超时场景下用户在 6s 内得到明确的失败反馈与下一步指引（不是无限等待）。

### 3.6 FR-06 优惠券咨询

- **用户故事**：作为用户，我希望问"满 100 减 30 的券为什么用不了"时得到具体原因（门槛/品类/有效期），而不是复制规则原文。
- **优先级**：P0
- **交互流程**：
  1. 意图识别为 VOUCHER_CONSULT → 调用 `query_voucher(voucherId?)`；用户未提供券 ID 时，先 `query_my_orders` 圈定其最近使用的券再查；
  2. LLM 结合券规则与用户订单上下文，定位不匹配的具体原因，输出「原因 + 解决路径」两段式回答；
  3. 若券适用于其他店铺 → 附带推荐："该券还适用于 XX 店（距您 1.2km）"。
- **边界条件**：
  - 券已过期/已使用 → 明确说明状态与时间点；
  - 规则字段缺失（运营录入不全）→ 诚实回答"规则暂未录入"，提供建单转运营核实路径，**禁止编造规则**（system prompt 硬约束 + 测试用例）；
  - 用户询问自己没有的券（"新人大礼包有什么"）→ 转化为平台活动介绍，仅描述结构性信息。
- **验收标准**：
  1. 券规则解释与数据库规则一致率 100%（对拍测试）；
  2. 规则缺失场景 20 条用例中 0 次出现编造（人工评审）；
  3. 端到端（含工具调用）P90 响应 ≤ 8s。

### 3.7 FR-07 商户信息咨询

- **用户故事**：作为用户，我希望咨询"XX 店现在营业吗、在哪"时获得实时准确的商户信息。
- **优先级**：P0
- **交互流程**：意图识别为 SHOP_CONSULT → 调用 `query_shop(shopId?)` / `search_shop_by_name` → 返回营业状态、地址、评分、人均；用户问及菜品/招牌等扩展信息时调用 `kb_search`（rag-service）检索商户知识库。
- **边界条件**：
  - 店名模糊匹配多个结果 → 列出候选让用户选择，不猜；
  - 商户知识库无该店资料 → 仅返回结构化字段，不补充想象内容；
  - 营业状态以 shop-service 实时数据为准，LLM 不得基于常识推测（如"一般商场店 10 点开门"这类回答禁止出现）。
- **验收标准**：
  1. 商户字段准确率 100%（对拍）；
  2. 模糊店名场景 100% 走候选确认路径（测试 20 条）；
  3. kb_search 检索的扩展信息必须带来源标注（"据商户资料"）。

### 3.8 FR-08 退款申请（人机协同核心）

- **用户故事**：作为用户，我希望 Agent 帮我把退款申请填好，我确认一下就能提交，不用自己找入口、写表单。
- **优先级**：P0
- **交互流程**：
  1. 意图识别为 REFUND → Agent 调用 `query_my_orders` 定位候选订单（若多单，让用户选择）；
  2. 生成**退款确认卡片**：订单摘要（券名/金额/下单时间）+ 退款原因下拉（选填：不要了/未收到/与描述不符/其他+文本框）+ 预计时效说明 + 「确认提交」「取消」按钮；
  3. 用户点击「确认提交」→ `POST /agent/chat/{sessionId}/confirm`（携带 actionId）；
  4. **后端二次校验**：订单归属（userId 匹配）、订单状态（未核销/未退款）、actionId 未消费（幂等）、卡片未过期（10 分钟有效）；
  5. 校验通过 → 执行退款申请落库（状态 REFUND_PENDING），返回受理编号，同步创建复核工单（FR-09）；
  6. 校验失败 → 返回具体原因（"订单状态已变更，请刷新查看"），卡片作废。
- **边界条件**：
  - 同一订单重复申请 → 二次校验拦截，提示已有进行中的退款申请及编号；
  - 订单已核销/已完成 → 卡片不可生成，说明不可退原因；
  - 用户点「取消」→ 卡片收起，对话继续（不建单、不留待办）；
  - 卡片过期后点击 → 提示重新发起；
  - 快速双击「确认提交」→ 幂等保证仅执行一次（压测用例：并发 10 次确认仅 1 条退款记录）。
- **验收标准**：
  1. 确认操作幂等：并发重复确认 100% 仅生效一次（自动化测试）；
  2. 越权（篡改 actionId/订单号）100% 拦截；
  3. 退款申请提交成功率 ≥ 99%（排除用户主动取消）；
  4. 从用户表达退款意图到卡片出现的 P90 时延 ≤ 8s。

### 3.9 FR-09 工单创建与自动路由

- **用户故事**：作为用户，我希望 Agent 解决不了的问题能自动变成一张有编号的工单，以便我随时查进度；作为人工客服，我希望工单已自动分好类和优先级，接手即可处理。
- **优先级**：P0
- **交互流程**：
  1. 投诉/疑难场景，Agent 结构化收集要素：问题类别（订单/券/商户服务/账号安全/其他）、涉及对象（订单号/券号/店铺）、发生时间、诉求；
  2. 调用 `create_ticket(category, priority, summary, refs)` 落库 `agent_ticket`，summary 为 LLM 生成的 ≤ 200 字客观摘要（不含主观评价与情绪词）；
  3. 路由规则：category → assignee_group（订单组/营销组/商户运营组/安全组）；priority 规则：涉及资金（退款失败/重复扣款）= 高，普通咨询 = 中，建议类 = 低；
  4. 返回工单号（形如 TK20260830000123）+ 预计处理时效（高：4h / 中：24h / 低：72h）；
  5. 发送 `agent-m5-ticket-route` MQ 消息，消费侧通知对应组。
- **边界条件**：
  - 要素不全（无法确定类别）→ 追问补全，最多 2 轮，仍不全则按"其他"建单；
  - 同一会话对同一问题重复建单 → 去重（同 category + 同 refs + 会话未关闭 → 返回已有工单号）；
  - 建单 API 失败 → 重试 1 次后降级为记录用户诉求 + 转人工，**不允许静默丢失用户诉求**；
  - summary 生成失败 → 使用规则拼接的模板摘要兜底。
- **验收标准**：
  1. 工单分类准确率 ≥ 90%（人工抽检 100 单）；
  2. 涉资金问题 priority=高的覆盖率 100%（规则测试）；
  3. 建单失败率 < 0.5%，且失败场景 100% 有降级出路（转人工）；
  4. 工单号唯一且可查询（FR-13）。

### 3.10 FR-10 转人工与上下文移交

- **用户故事**：作为用户，当 Agent 解决不了或我不想和机器说话时，我希望能立刻找到真人，且不用重新描述一遍问题。
- **优先级**：P0
- **交互流程**：
  1. 触发条件（任一）：用户显式要求（"转人工"）；连续 2 次工具调用失败；澄清 2 轮仍无法确定意图；用户情绪检测为强烈负面（词典 + 规则初版，不做模型分类）；
  2. Agent 停止生成，推送转人工卡片：「即将为您转接人工客服」+ 摘要预览（可折叠，展示 LLM 生成的对话摘要：用户身份/诉求/已查到的事实/未解决的问题）；
  3. 用户确认 → 会话状态置 TRANSFERRED，进入人工队列（本作品集阶段为模拟坐席：P2 工作台接收；无坐席在线时留言入工单）；
  4. 移交数据包：完整对话历史 + 摘要 + 已调用的工具结果快照（订单卡片等）。
- **边界条件**：
  - 无人值守时段 → 直接建单（FR-09）并告知预计响应时效；
  - 用户在等待人工时继续发消息 → 消息进入队列随移交包带给人工；
  - 转人工触发后 Agent 不得再继续生成内容（状态锁）。
- **验收标准**：
  1. 四类触发条件各自 100% 触发（各 20 条用例）；
  2. 移交包中摘要包含"身份/诉求/已查事实/待解决"四要素的完整率 ≥ 95%（人工抽检）；
  3. 触发转人工后 Agent 零后续输出（日志验证）。

### 3.11 FR-11 安全风控

- **用户故事**：作为平台，我需要防止客服入口被滥用（高频刷量、注入攻击、敏感内容），保障服务可用与合规。
- **优先级**：P0
- **交互流程与规则**：
  1. **频控**（网关令牌桶）：单用户 10 QPS、单用户日会话数上限 20 次（超出提示明日再试）；单会话消息数上限 100 条；
  2. **输入安全**：用户消息进入 LLM 前过敏感词与注入特征检测（正则规则库：忽略此前指令/你现在是/role override 等模式）；命中 → 不进入 LLM，返回固定话术并记审计；
  3. **输出安全**：LLM 输出过敏感词二次过滤；命中 → 丢弃该段重新生成（最多 1 次），再命中则返回兜底话术 + 建议转人工；
  4. **AI 生成内容标识**：对话页顶部与关于页固定标识"本服务由 AI 提供，内容由人工智能生成"（合规要求）；
  5. **数据红线**：LLM 上下文不注入用户手机号明文、支付凭证；工具结果中的敏感字段脱敏后再进入上下文。
- **边界条件**：
  - 频控触发 → 返回 429 语义的友好提示，不封禁会话（次日自动恢复）；
  - 注入检测误伤正常表达（如用户复述"客服让我忽略规则"）→ 人工申诉通道（建单）；
  - 敏感词库需支持热更新（配置中心，不发版生效）。
- **验收标准**：
  1. 注入攻击测试集（30 条，含中英文/变体写法）拦截率 100%；
  2. 频控边界测试：11 QPS 触发限流、9 QPS 不触发；
  3. 敏感词热更新 1 分钟内生效；
  4. 全部会话与拦截事件在审计表可查（100% 留痕）。

### 3.12 FR-12 会话评价

- **用户故事**：作为平台，我需要用户对每次服务打分，以便量化 Agent 质量并持续优化。
- **优先级**：P1
- **交互流程**：会话结束（用户主动结束/超时关闭/转人工后）推送评价卡片：满意/不满意 + 不满意时的多选标签（没解决问题/答非所问/操作太复杂/其他）。评价数据入 `agent_session.rating`。
- **边界条件**：每会话仅一次评价；用户忽略则 24h 后不再提醒；评价不匿名（内部产品阶段，绑定 userId 便于回溯会话）。
- **验收标准**：评价提交成功率 100%；埋点上报率 ≥ 99%。

### 3.13 FR-13 会话历史与工单进度查询

- **用户故事**：作为用户，我希望能翻看历史咨询记录、凭工单号查进度，以便跟进没解决完的问题。
- **优先级**：P1
- **交互流程**：「我的 → 客服记录」列表（最近 30 天会话，含状态与评价标记）；会话详情支持回放（文本 + 卡片快照，工具过程不回放）；工单进度页展示状态流转（OPEN→ROUTED→RESOLVED）与处理备注。
- **边界条件**：回放为静态快照不可继续对话（需新建会话，入口按钮「基于此会话继续咨询」自动携带摘要）；会话数据保留 90 天后归档。
- **验收标准**：列表加载 P90 ≤ 1s；回放内容与实时会话一致率 100%（快照存储验证）。

### 3.14 FR-14 客服工单工作台（内部）

- **用户故事**：作为人工客服，我希望在一个工作台里看到分配给我的工单与转人工会话，处理完毕后关闭工单并记录处理结果。
- **优先级**：P2
- **交互流程**：工单列表（按组过滤、优先级排序）→ 工单详情（用户摘要/关联会话回放/处理表单：处理结果 + 备注）→ 关闭工单（状态 RESOLVED，可选触发用户通知）；接收 TRANSFERRED 会话进入人工接管模式（文本回复）。
- **边界条件**：本阶段为演示级实现（无排班/质检）；人工接管的消息走同一 SSE 通道，区分 `role=human`。
- **验收标准**：工单状态机流转正确（非法状态跳转 100% 拦截）；人工接管消息实时到达（≤ 2s）。

## 4. 非功能需求（NFR）

### 4.1 性能指标

| 指标 | 目标 | 测量口径 |
|---|---|---|
| SSE 建连 + 首 token 延迟 P90 | ≤ 1.5s | 前端埋点：连接发起 → 首个 `delta` 事件 |
| 纯对话完整响应 P90 | ≤ 5s | 首消息 → `done` 事件 |
| 含 1 次工具调用的响应 P90 | ≤ 8s | 同上（含工具往返） |
| 工具调用延迟 P95 | ≤ 2s（Feign 超时上限） | agent_tool_call.latency_ms |
| 并发会话数（单实例 2C4G） | ≥ 50，错误率 < 1% | Gatling 压测 10 分钟 |
| 会话历史读取 P90 | ≤ 100ms | FR-13 列表接口 |
| 单会话平均 Token 成本 | ≤ ¥0.05（flash 档）/ ≤ ¥0.15（GLM-5 档） | token_cost 聚合 |

**性能设计约束**（开发必读）：SSE 全链路基于 Spring MVC 异步 Servlet 实现，严禁在 Tomcat 工作线程上同步阻塞等待 LLM 响应；工具调用在编排层并行化（无依赖的工具用 CompletableFuture 并发执行）。

### 4.2 安全要求

| 类别 | 要求 |
|---|---|
| 认证与会话 | 复用 Sa-Token/JWT 登录态；sessionId 与 userId 强绑定，服务端校验所有会话操作归属 |
| 授权 | 工具层强制 userId 过滤（数据查询永不信任 LLM 传入的归属参数）；确认操作后端二次校验（见 FR-08） |
| 注入防护 | 用户输入注入特征检测 + system prompt 加固（工具结果以"数据"而非"指令"格式注入）；LLM 输出敏感词过滤 |
| 数据安全 | 手机号/支付信息脱敏进入 LLM 上下文；会话数据保留 90 天；审计表不可篡改（仅追加） |
| 合规 | AI 生成内容显著标识（4.11 FR-11）；不采集与服务无关的个人信息；用户可申请删除历史会话（工单通道受理） |
| 审计 | 全量 agent_tool_call 留痕（参数/结果/耗时/trace_id），支持按会话回放追溯 |

### 4.3 可用性与降级

| 场景 | 降级策略 |
|---|---|
| LLM 上游故障/超时 | 3 次重试（指数退避）后切换备用模型（glm-4-flash ↔ GLM-5）；仍失败 → 返回 FAQ 直答（rag-service 检索 top1 原文）+ 建单入口 |
| 工具调用失败 | 重试 1 次 → Observation 告知 LLM 换路 → 连续 2 次失败触发转人工（FR-10） |
| rag-service 故障 | 客服主链路不依赖 RAG（仅 FR-07 扩展信息用到），核心工具链路不受影响 |
| 整体可用性目标 | ≥ 99.5%（月度），以 SSE 建连成功率为口径 |

### 4.4 兼容性范围

| 端 | 范围 |
|---|---|
| 浏览器 | Chrome/Edge ≥ 100、Safari ≥ 15、移动端 WebView（微信内置浏览器）；SSE 不支持时自动降级轮询（3s 间隔） |
| 分辨率 | 375px（移动）~ 1920px（桌面）响应式 |
| 后端依赖 | Java 21 / Spring Boot 3.1.12；服务间 OpenFeign；基础设施复用 Nacos/Redis/RocketMQ/MySQL/PgVector 既有实例 |
| 模型 | GLM-5 + glm-4-flash（OpenAI 协议兼容），接口抽象层保证可替换为 DeepSeek/通义 |

### 5.3 核心页面流程

**流程 A：订单查询（主路径）**

```
[用户] 输入"我上周抢的券怎么没到"
  → [AI] tool_call 状态条"正在查询订单…"（≤1.5s 出现）
  → [AI] 订单卡片列表（3 条，按时间倒序）
  → [用户] 点选第 2 条 / 追问"这个未支付什么意思"
  → [AI] 状态解释 + 支付引导
  → [用户] 满意离开 / 继续其他意图
```

**流程 B：退款（含人机协同）**

```
[用户] "这个券不要了，退款"
  → [AI] 定位订单（多单则列出选择）
  → [AI] 退款确认卡片（订单摘要+原因选择+确认/取消）
  → [用户] 选原因 → 点击「确认提交」
  → [系统] 二次校验（归属/状态/幂等/时效）
       ├─ 通过 → 受理编号 + 自动创建复核工单 → [AI] 告知结果与时效
       └─ 失败 → 卡片作废 + 具体原因提示
  → [AI] 会话结束推送评价卡片
```

**流程 C：投诉建单**

```
[用户] "这家店态度太差，投诉"
  → [AI] 安抚 + 要素收集（店铺/时间/问题类型，最多 2 轮追问）
  → [AI] create_ticket → 返回工单号 TK… + 预计时效
  → [用户] 可凭工单号在「我的工单」查进度
```

**流程 D：转人工**

```
触发（显式要求/工具连败×2/澄清超限/负面情绪）
  → [AI] 转人工卡片（摘要预览可折叠）
  → [用户] 确认 → 状态 TRANSFERRED
       ├─ 有坐席（P2）→ 人工接管，消息实时互通
       └─ 无坐席 → 自动建单（沿用摘要）+ 告知时效
```

## 6. 数据需求与埋点方案

### 6.1 数据模型（agent_service 库）

沿用总体 PRD 已定义的表，本模块涉及：

| 表 | 用途 | 关键字段 |
|---|---|---|
| agent_session | 会话主表 | module='M5'、status、summary、rating、token_cost |
| agent_tool_call | 工具调用审计 | session_id、tool_name、args、result、latency_ms、success、trace_id |
| agent_task | 确认卡片/退款申请 | task_type='REFUND_REQUEST'、status（PENDING_CONFIRM/ADOPTED/REJECTED/EXPIRED） |
| agent_ticket | 工单 | category、priority、summary、refs（订单/券/店铺引用）、status、assignee_group |

补充字段（本 PRD 新增）：`agent_session.rating TINYINT`（1-5，可空）、`agent_session.transfer_reason VARCHAR(32)`（HUMAN_DEMAND/TOOL_FAIL/CLARIFY_EXCEED/NEGATIVE_EMOTION）、`agent_ticket.dedup_key VARCHAR(64)`（同会话去重键）。

### 6.2 埋点方案

**事件规范**：`事件名 = 模块_对象_动作`，属性含 `sessionId/userId/timestamp(服务端)`；前端埋点走统一上报接口，服务端关键事件由 agent-service 直接写入（不依赖前端，保证准确率）。

| 事件 | 触发时机 | 关键属性 | 用途 |
|---|---|---|---|
| m5_session_start | SSE 建连成功 | entry（my/order_detail/voucher_detail） | 入口分析 |
| m5_msg_send | 用户发送消息 | msgLen、roundNo | 活跃度 |
| m5_first_token | 首个 delta 到达 | 延迟 ms | 性能北极星 |
| m5_tool_call | 每次工具调用 | toolName、success、latency | 工具质量 |
| m5_intent | 意图识别完成 | intent、confidence、clarifyRound | 意图准确率监控 |
| m5_refund_card_show | 退款卡片曝光 | orderId | 漏斗 |
| m5_refund_confirm | 用户确认退款 | 通过/失败原因 | 漏斗 + 二次校验监控 |
| m5_ticket_create | 工单创建 | category、priority | 建单量 |
| m5_transfer_human | 转人工触发 | transferReason | 转人工率归因 |
| m5_session_end | 会话结束 | 消息数、持续时长、是否解决（推断） | 一次解决率 |
| m5_rating_submit | 评价提交 | score、tags | 满意度 |

**漏斗定义（监控看板）**：

```
会话开始 → 意图识别成功 → 工具调用成功 → 问题解决（无转人工/无同因二次会话）
```

### 6.3 核心指标口径

| 指标 | 口径 | 目标 |
|---|---|---|
| 一次解决率（北极星） | 分子：会话结束无转人工，且 24h 内无同 category 新会话；分母：全部已结束会话 | ≥ 70% |
| 转人工率 | TRANSFERRED 会话 / 全部会话 | ≤ 20% |
| 意图识别准确率 | 抽样人工标注 vs 埋点 intent | ≥ 95% |
| 工具调用成功率 | success=true / 全部调用 | ≥ 99% |
| 退款确认转化 | m5_refund_confirm(通过) / m5_refund_card_show | ≥ 60% |
| 会话满意度 | rating ≥ 4 的评价占比 | ≥ 80% |

## 7. 项目里程碑与发布计划

**总周期 5 周（对齐总体 PRD 的 W1-W5 MVP 段）**：

| 里程碑 | 时间 | 交付内容 | 退出标准（验收） |
|---|---|---|---|
| MS1 底座就绪 | W1-W2 | agent-service 骨架：会话/SSE/ToolRegistry/ReAct 循环/短期记忆/审计表；FR-01/02/04 基础版；1 个工具（query_my_orders）端到端 | curl 走 SSE 完成一次带工具调用的问答；agent_tool_call 完整留痕 |
| MS2 功能全量 | W3 | FR-03/05/06/07/08/09/10/11 全部 P0 功能；澄清菜单、确认卡片、转人工 | 全部 P0 功能的自动化用例（对拍/幂等/越权/注入）通过率 100% |
| MS3 打磨与 P1 | W4 | FR-12/13；埋点全量接入；Grafana 看板（业务+工程双面板）；Gatling 压测报告 | 埋点上报率 ≥ 99%；压测达 4.1 节指标 |
| MS4 发布 | W5 | 灰度发布：10% 用户 → 50% → 100%（每档观察 ≥ 24h）；演示脚本与面试问答手册 | 灰度期间转人工率 ≤ 25%、P0 缺陷清零 |

**发布与回滚**：

- 发布方式：Nacos 配置灰度开关 `agent.m5.enabled + 流量百分比`，按 userId 哈希分桶；
- 回滚预案：开关一键关闭 → 入口回退到原"留言反馈"页；已创建会话与工单数据保留不删；
- 数据观察窗口：全量后连续 7 天日报（一次解决率/转人工率/成本/工具成功率）。

## 8. 风险预估与应对预案

| # | 风险 | 概率 | 影响 | 应对预案 |
|---|---|---|---|---|
| R1 | LLM 幻觉：编造订单状态/券规则 | 中 | 高 | 架构性缓解：所有事实类回答强制来源于工具返回，system prompt 硬约束"无工具数据不得陈述事实"；测试集持续对拍；线上抽检机制（每日 20 条人工评审） |

| R3 | Prompt 注入导致越权/违规输出 | 中 | 高 | FR-11 三层防护（输入检测/prompt 加固/输出过滤）；30 条攻击用例回归；命中即审计留痕 |
| R4 | 退款误执行（重复退款/越权退款） | 低 | 高 | 双闸门：确认卡片 + 后端二次校验（归属/状态/幂等）；actionId 一次性消费；每日对账脚本核对退款数与确认数 |
| R5 | Token 成本超标 | 中 | 中 | 历史裁剪 + 摘要压缩；意图分流（CHAT 类走 glm-4-flash）；会话级成本预算，超限提示结束并建单；看板日监控 |
| R6 | 工具调用放大 order/voucher 服务延迟（拖垮上游） | 中 | 高 | Feign 2s 超时 + 单次重试；网关侧 agent 路由独立限流（10 QPS/用户）；工具层加 Sentinel 熔断，上游异常时快速失败走降级 |
| R7 | 用户信任度低（不敢用 AI 办退款） | 中 | 中 | 工具过程可视化（FR-04）+ 确认卡片明确告知影响 + 转人工常驻入口；满意度数据驱动话术迭代 |
| R8 | 情绪识别误判（把玩笑当愤怒转人工） | 中 | 低 | 初版仅用词典+规则（高置信才触发）；误判反馈进入周迭代 |

| R10 | 合规风险（AI 内容标识缺失/敏感内容流出） | 低 | 高 | FR-11 固定标识进 P0 验收项；输出敏感词过滤为发布前置条件；保留审计日志备查 |

## 附录 A：术语表

| 术语 | 定义 |
|---|---|
| ReAct | LLM 交替进行推理（Thought）与工具调用（Action-observation）的 Agent 编排模式，本项目最大 8 步 |
| 确认卡片（Confirm Card） | Agent 产出待执行写操作时推送的 UI 卡片，用户显式确认后后端才执行 |
| 二次校验 | 后端在执行确认操作前独立复核权限/状态/幂等，不信任前端与 LLM 的任何中间结论 |
| 一次解决率 | 单次会话解决问题且 24h 内无同类别新会话的比例 |
| Observation | 工具调用结果以数据形式回填给 LLM 的文本，是 ReAct 循环的输入 |
| 对拍测试 | 将 Agent 经工具返回的数据与数据库直查结果自动比对的测试方法 |
