## 0. 文档定位

本套规格**只收录会导致错误行为的系统缺陷与安全漏洞**——即"代码运行起来会产生错误结果、丢数据、越权或被绕过"的问题。

**不收录**以下三类（已按项目方口径确认，不属于待修复缺陷）：

| 类别 | 说明 |
|------|------|
| 技术选型演进的历史遗留配置 | 如已从 Seata 迁移到 Redis+Lua+RocketMQ 后残留的 Seata 配置——属于已废弃方案，不影响运行 |
| 性能基线与压测口径 | 商户查询 QPS 21027、本地缓存（Caffeine）的使用——**按项目方提供的基线采信**，本文档不做核验，仅在下文记为既定事实 |
| MQ 更换造成的类更替 | 从 RabbitMQ 迁移到 RocketMQ 后，原 RabbitMQ 解耦相关类（`MqConfig`/`MqMessageSender`）不再存在——属预期结果 |

**性能基线（既定事实，供各 SPEC 引用）**：商户信息查询接口 QPS **≥ 21027**，测试环境 8 核 16 GB。

## 2. 排序与理由

排序遵循 **"阻断性 > 正确性 > 安全性 > 可靠性 > 卫生性"**，同级内按依赖方向拓扑排序。

### 2.1 P0 — 阻断级（不改则核心链路不可用、无法验证）

| 序 | SPEC | 为什么排在这个位置 |
|----|------|-------------------|
| 1 | **SPEC-01** 网关路由 | 秒杀、我的订单、退款三个入口经网关**必然 404**。在修复前，SPEC-03/04 的端到端验收无从执行；前端 100% 流量经网关，故对真实用户完全不可用 |
| 2 | **SPEC-02** 数据层 DDL | `tb_shop` 建成了 blog 结构，真正的商户表与 `tb_blog`/`tb_blog_comments`/`tb_user` 完全缺失。任何按仓库脚本初始化的环境，商户与社交服务首次查询即 SQL 报错 |
| 3 | **SPEC-03** 秒杀主链路 | 库存双扣、消息静默丢失、消费失败静默 ACK——**直接造成资金/库存错误与订单丢失**，是风险最高的一类 |
| 4 | **SPEC-04** 补偿与对账 | 对账接口返回"成功"却零写入、检查恒判"正常"，使 SPEC-03 造成的数据发散**无法被发现也无法收敛** |

**1 与 2 可并行**（互不依赖，均为验证前置）。**3 必须先于 4**：SPEC-04 的补偿逻辑要读取 Redis 订单明细 key，而该 key 当前在写入端、删除端、读取端有**三种不同拼法**；不先在 SPEC-03 冻结契约，补偿任务会读到错误 key 并制造二次脏数据。

### 2.2 P1 — 高（正确性与安全）

| 序 | SPEC | 理由 |
|----|------|------|
| 5 | **SPEC-05** 缓存正确性 | 负缓存 30 分钟使**新增商户长时间不可见**；预热 `@PostConstruct + @Async` 失效并**阻塞启动 10 秒**；`queryWithMutex` 存在**锁误删**逻辑。属实打实的功能与并发缺陷 |
| 6 | **SPEC-06** 鉴权与越权 | 安全等级最高（内部扣库存端点无鉴权、任意登录用户可执行管理操作）。**若服务将对公网暴露，应与 P0 同批上线** |
| 7 | **SPEC-07** Feign 契约 | `/user/list` 端点不存在 → 点赞排行榜与共同关注**必然不可用**；且它是 SPEC-09 的前置 |

> **SPEC-06 与 SPEC-07 必须同批实施**：为业务服务加装鉴权拦截器后，order→voucher、social→user 未透传 token 的 Feign 调用会被 401 拒绝，秒杀链路将整体中断。二者存在强耦合。

### 2.3 P2 — 中（可靠性与治理）

| 序 | SPEC | 理由 |
|----|------|------|
| 8 | **SPEC-08** MQ 可靠性 | 死信链路双向断开、social/rag 消费者无幂等（重复投递产生重复数据）、发送失败静默丢单。建立在 SPEC-03/04 已止血的链路之上 |
| 9 | **SPEC-09** 社交/业务 | 评论可伪造身份、点赞数可为负、退款订单永久卡在"退款中"。依赖 SPEC-02 与 SPEC-07 |
| 10 | **SPEC-10** 配置与运行时 | `RedissonConfig` 读取不存在的配置键（host 恒为 localhost）、5 个服务加载不到 RedissonClient、中间件无 compose、`RedisIdWorker` 无时钟回拨防护。无强依赖，可并行 |

### 2.4 P3 — 卫生

| 序 | SPEC | 理由 |
|----|------|------|
| 11 | **SPEC-11** 死代码与注释失真 | 纯清理。**关键目标**：删除"零引用且带缺陷"的代码（如依赖不存在的 `unlock.lua` 的 `SimpleRedisLock`、含锁误删的 `CacheClient`），避免后续被误用；并修正与实现不符的代码注释。不产生新行为，任何时候执行都不影响其他 SPEC |

## 4. 编制过程说明

为保证结论可靠，以下两项**曾疑为缺陷、经逐行复核后被排除**，已不作为问题记录：

1. **`BlogServiceImpl` 未标注 `@Slf4j` 却使用 `log`** —— 实际可正常工作：MyBatis-Plus 的 `ServiceImpl` 父类声明了 `protected org.apache.ibatis.logging.Log log`（经 `javap` 验证），`mvn compile` 亦为 exit 0。
2. **`queryBlogOfFollow` 的 `os` 游标疑似 off-by-one** —— 逐行复核确认**语义正确**：`os` 统计本页最小分值出现次数，下轮 `reverseRangeByScoreByScore(key, 0, minTime, os, 2)` 恰好跳过已返回的同分值记录。

两处均已在对应 SPEC 中显式标注，以免后续误改。
