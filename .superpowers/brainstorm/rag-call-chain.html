🔗 代码级调用链

① 网关鉴权 —— Sa-Token + Rediscommon/SaTokenConfig.java

网关是所有请求的唯一入口（gateway-service:8081）。每个 HTTP 请求到达时，网关的 Sa-Token 全局过滤器拦截请求，从 Header 中取出 Authorization 字段的 token 值。

然后通过 StpUtil.getLoginIdByToken(token) 向 Redis 查询这个 token 对应的会话信息。Redis 中存储了登录用户的 userId、角色、权限等数据；所有微服务共享同一个 Redis 集群，所以任何服务拿到的用户信息都是一致的。

校验通过后，网关将用户信息写入请求头（如 X-User-Id: 1002），转发到 rag-service:8087。rag-service 内部的 Sa-Token 拦截器从请求头读取 userId，调用 UserHolder.saveUser(userDTO) 将其存入 ThreadLocal。此后当前线程的任何代码都可以通过 UserHolder.getUser().getId() 拿到 userId=1002。

ThreadLocal 是 Java 提供的一个线程本地存储机制，每个线程有自己的独立副本，互不干扰。把用户信息存进 ThreadLocal，后续任何方法都不用传参就能拿到"当前用户是谁"，不需要在每个方法签名里加 userId 参数。
Sa-Token 的会话数据全部存在 Redis 中（配置了 sa-token-redis-jackson），不是存在 JVM 内存里。这样即使 rag-service 重启，用户的登录状态也不会丢失；多个微服务实例也能共享同一份会话。
② QaController —— 接收请求 + 异步审计QaController.java :30-50

请求到达 QaController.chat() 方法。这个方法的返回值类型是 Flux<String>（Reactor 的反应式流类型），意味着它会持续向客户端推送数据，不是一次性返回。

方法做的第一件事：UserHolder.getUser().getId() 从 ThreadLocal 取出 userId=1002。同时 httpRequest.getRemoteAddr() 获取客户端 IP。然后立即调用 auditService.log() 记录审计日志——这一步标注了 @Async，在另一个线程中执行，不阻塞主流程。即使审计写 DB 失败了，问答也照常进行。

然后调用 qaPipeline.answer(question, kbId, topK, enableRerank, messages)，把核心逻辑交给 Pipeline 层。返回的 Flux<String> 会经过 Controller 再拼接上 thinking 事件和 done 事件，形成完整的 SSE 流。

SSE（Server-Sent Events）是一种 HTTP 长连接技术。普通 HTTP 是"请求→响应→断开"，SSE 是"请求→保持连接→服务器持续推送→推送完毕才断开"。前端可以用 EventSource API 接收。Flux<String> 是 Spring Reactor 的反应式流类型，可以理解为一个"数据管道"——生产者往里塞数据，消费者（前端）从另一端实时收到。
为什么 Controller 要用 Flux 而不是普通 String？因为 LLM 生成答案需要几秒钟，如果等全部生成完毕再返回，用户看到的是白屏转圈 4 秒然后突然出现一坨文字。用 Flux 流式推送，LLM 每生成一个汉字就立刻推到前端，体验像 ChatGPT 那样逐字出现。

④ HybridRetriever —— 混合检索调度检索HybridRetriever.java :22-33

HybridRetriever 本身不做检索，它的职责是调度两个子检索器并行工作，然后合并结果。这种模式叫"混合检索"（Hybrid Search）——同时用两种不同策略搜，再融合。

④-a VectorRetriever —— 语义向量检索检索VectorRetriever.java :23-42

向量检索的核心思想：把文字变成一组数字（向量），语义相近的文字，数字也相近。搜的不是"文字匹配"，而是"意思相近"。

它做了两件事：（1）调 Embedding API 把问题转成 1024 个浮点数（2）拿这组数字去 PgVector 数据库里找最相似的 chunk。

④-a-1 GlmEmbeddingClient.embed() —— 文字→数字APIGlmEmbeddingClient.java :42-83

调用智谱的 Embedding API：

POST https://open.bigmodel.cn/api/paas/v4/embeddings

请求体：{"model": "embedding-2", "input": ["招牌菜是什么？"]}

响应体：{"data":[{"embedding":[0.0123, -0.0456, 0.0789, ...]}]} —— 共 1024 个浮点数

这是一个黑盒过程：GLM 的 Embedding 模型把输入的文字"投影"到了一个 1024 维的数学空间。在这个空间里，"招牌菜是什么"和"本店特色菜包括水煮鱼"这两句话的向量坐标非常接近（余弦相似度 ≈ 0.92），而"招牌菜是什么"和"营业时间周一至周日"的坐标非常远（余弦相似度 ≈ 0.15）。

代码还实现了指数退避重试：如果 API 返回 429（限流）或 5xx（服务器错误），等待 1s→2s→4s 后重试，最多 3 次。401/403 等鉴权错误不重试（重试也没用）。

Embedding（嵌入）就是把文字映射到高维数字空间。可以想象成一张大地图，每个词、每句话都有一个经纬度坐标。"水煮鱼"和"麻辣鱼"的坐标挨得很近，"水煮鱼"和"结账"的坐标隔着很远。当你问"招牌菜"，系统就去地图上找离你问题最近的几个坐标点。
为什么是 1024 维而不是 256 或 4096？维度越高，表达能力越强（能区分更细微的语义差异），但存储和计算成本也越高。1024 是 GLM Embedding-2 模型的固定输出维度，业界主流 Embedding 模型也多在这个范围（OpenAI text-embedding-3-large 是 3072 维，BGE-M3 是 1024 维）。
④-a-2 DocumentChunkRepository.vectorSearch() —— PgVector 相似度搜索SQLDocumentChunkRepository.java :69-76

把 1024 维向量传进 PgVector 执行余弦相似度搜索：

SELECT id, content, metadata,
       1 - (embedding <=> '[0.0123,-0.0456,...]'::vector) AS similarity
FROM rag_document_chunk
WHERE kb_id = 1                        ← 只搜当前商户的知识库
ORDER BY embedding <=> '[0.0123,...]'::vector
LIMIT 10;

SQL 中 <=> 是 PgVector 扩展提供的余弦距离运算符。它计算两个向量在 1024 维空间中的夹角，返回 0（完全相同）到 2（完全相反）之间的值。用 1 - 距离 换算成 0 到 1 的相似度分数。

搜索时使用了 IVFFlat 索引加速：预先将 1024 维空间划分为 100 个聚类（lists=100），查询时先定位到最近的几个聚类中心，只在这些聚类内做精确搜索，避免了全表扫描。万级 chunk 量级下，检索延迟约 50-100ms。

WHERE kb_id = 1 这一行是关键——权限隔离。即使向量相似度再高，也只返回属于当前商户知识库的 chunk，不会把餐厅 A 的内部文件搜给餐厅 B 的用户看。

余弦相似度 vs 欧几里得距离：欧几里得距离是两点之间的直线距离（受向量长度影响），余弦相似度只看夹角（不受长度影响）。在 NLP 领域，余弦相似度更常用，因为两段文字的长度不影响语义相似度——"水煮鱼"和"水煮鱼 38元一份 麻辣鲜香"在向量空间中方向一致，长度不同但语义高度相关。
为什么不直接用 SELECT * 然后 Java 代码里算相似度？因为数据量一大（几千个 chunk），把全部数据拉到 Java 内存再排序，网络传输 + 内存开销太大。让数据库带着索引直接算好 Top-10 返回，只传 10 条数据，效率高几十倍。

④-b KeywordRetriever —— 关键词全文检索检索KeywordRetriever.java :21-36

和向量检索同时进行。不调任何外部 API，直接查 PostgreSQL 的 tsvector 全文索引。调用链：chunkRepo.keywordSearch("招牌菜是什么？", kbId, 10)。

PostgreSQL 的 plainto_tsquery('chinese', '招牌菜是什么') 会自动对中文分词——把一句话切成有意义的词：'招牌菜' | '什么'（"是"和"吗"是停用词被过滤）。然后拿这些词去 tsvector 索引里匹配。

tsvector 是怎么来的？在文档上传入库时（DocumentPipeline），每条 INSERT 都用 to_tsvector('chinese', content) 把中文文本预处理成倒排索引：每个词出现的位置、频率都会被记录。这是数据库自动做的，不需要额外代码。

倒排索引就像书的附录索引：普通索引是"第几章讲什么"，倒排索引是"某个词出现在哪几章"。你查"水煮鱼"，倒排索引直接告诉你"它在 chunk_2 第 3 位、chunk_5 第 1 位、chunk_9 第 8 位"，不用扫描每个 chunk 的内容。
④-b-1 DocumentChunkRepository.keywordSearch()SQLDocumentChunkRepository.java :73-76
SELECT id, content, metadata,
       ts_rank(tsv, plainto_tsquery('chinese', '招牌菜是什么')) AS score
FROM rag_document_chunk
WHERE kb_id = 1
  AND tsv @@ plainto_tsquery('chinese', '招牌菜是什么')
ORDER BY score DESC
LIMIT 10;

@@ 是 PostgreSQL 的全文匹配运算符，意思是"tsv 列里有没有这些词"。ts_rank() 是 TF-IDF 加权排名函数——词频越高、出现在越少文档中的词权重越大。GIN 索引让这个查询在万级数据里只需要几毫秒。

④-c RrfFusion.merge() —— 倒数排名合并融合RrfFusion.java :16-45

RRF（Reciprocal Rank Fusion，倒数排名融合）是一种不依赖原始分数的排名合并算法。它不关心向量的余弦相似度是 0.91 还是 0.65，也不关心 ts_rank 是 0.34 还是 0.01——它只关心排名。

核心公式非常简洁：分数 = 1 / (k + rank)，其中 k=60（可配置的平滑因子），rank 从 1 开始。合并时同一 chunk 出现在两个列表里就累加。

        向量排名(i)     RRF分=1/(60+i+1)         关键词排名     RRF分=1/(60+j+1)      融合总分
chunk_5  第1名   →     1/61 = 0.01639      chunk_2  第1名  →   1/61 = 0.01639
chunk_2  第2名   →     1/62 = 0.01613      chunk_5  第2名  →   1/62 = 0.01613
chunk_8  第3名   →     1/63 = 0.01587      chunk_1  第3名  →   1/63 = 0.01587
chunk_1  第4名   →     1/64 = 0.01563      chunk_9  第4名  →   1/64 = 0.01563
chunk_3  第5名   →     1/65 = 0.01538      chunk_4  第5名  →   1/65 = 0.01538

                                                           ↓ 合并累加 ↓
chunk_5: 0.01639 + 0.01613 = 0.03252  ← 两路都排前，总分最高
chunk_2: 0.01613 + 0.01639 = 0.03252  ← 同样高分
chunk_8: 0.01587 + 0.012 = 0.016     ← 向量前3，关键词也有分
chunk_1: 0.01563 + 0.01587 = 0.03150  ← 两路都有，排第4
chunk_9: 0.008 + 0.01563 = 0.016      ← 关键词排前但向量靠后

最终按融合分数降序取 Top-5：[chunk_5, chunk_2, chunk_1, chunk_8, chunk_9]

RRF 的精妙之处在于"去量纲"——向量的余弦相似度（0.9-0.3）和 keyword 的 ts_rank（0.3-0.01）数值范围完全不同，如果直接加权相加（如 0.6×cos + 0.4×tsrank），结果会严重偏向数值大的那一路。RRF 只看排名不看分数绝对值，完美解决了不同检索器的分数不可比问题。k=60 是经验值，k 越大排名靠后的项得到的分数越接近（平滑效果越强），k 越小头部效应越明显。
如果不做融合，只靠向量检索会导致"看不见精确关键词"的问题（比如搜"38元"可能返回一些语义相关但不含价格的 chunk）；只靠关键词检索会导致"理解不了同义词"的问题（搜"辣的鱼"搜不到"水煮鱼"）。两路融合后取长补短。

⑤ 可选重排序编排QaPipeline.java :41-43 → NoOpReranker.java

当前 enableRerank=false，走 NoOpReranker：不做任何精排，直接截断取前 5 条返回。

Reranker 的真正价值在于Cross-Encoder 精排。前面的向量检索用的是 Bi-Encoder（问题和文档各自独立编码再算相似度，速度快但精度有限）。Cross-Encoder 把"问题+文档"拼在一起输入模型做深度交叉比对，精度高得多但速度慢（每对都要推理一次）。实践中一般 Bi-Encoder 粗排 Top-20 → Cross-Encoder 精排 Top-5。

代码预留了 IReranker 接口，未来只需要实现一个 CohereReranker 或 JinaReranker（调 API 即可），QaPipeline 一行不用改。

Bi-Encoder vs Cross-Encoder 的经典比喻：Bi-Encoder 像"看两个人分别的简历"，快速判断他们是否匹配；Cross-Encoder 像"让两个人面对面聊 5 分钟"，判断更准但成本高。实际工程中先 Bi-Encoder（≈50ms 筛 20 个候选），再 Cross-Encoder（≈200ms 精排 5 个）。

这里有几个关键设计考量：

① 明确"没有找到相关信息"的边界——如果不加这句，LLM 遇到知识库不涵盖的问题时会编造答案（幻觉）。加了之后就变成了"我查了资料，没找到"。

② 每个 chunk 标了来源 ID（【来源5】），不是直接拼文本。这样 LLM 生成答案后可以反向追溯到原文——实现"可溯源的 AI 回答"，用户看到答案可以验证出处。

③ Prompt 是中文的——不是中英混杂。中文 Prompt 对 GLM-5 的效果优于英文 Prompt，因为 GLM 对中文语义的理解更自然。

System Prompt vs User Message：System Prompt 是给 AI 的"角色设定"（你是谁、用什么语气、基于什么知识回答）。User Message 是用户直接问的问题。AI 会把 System Prompt 当作更高级别的指令来遵守——所以"没有信息时如实告知"写在 System Prompt 里比写在 User Message 里更有效。
⑦ 裁剪多轮对话历史编排QaPipeline.java :48-51

客户端会传一个 messages 数组，包含之前的对话历史（多轮对话的上下文）：

[{"role":"user","content":"你好"}, {"role":"assistant","content":"您好！"}, ...]

如果历史太长，所有 message 一起塞给 LLM 会超出 token 限制（GLM-4-flash 的上下文窗口约 128K tokens，但 Prompt 越长生成越贵越慢）。代码裁掉前面的旧消息，只保留最近 10 轮（20 条消息，10 个用户消息 + 10 个 AI 回复）。

Token（令牌）是 LLM 计费和处理的基本单位。中文一个字 ≈ 1.5-2 token，英文一个单词 ≈ 1-2 token。上下文窗口 128K 意味着 LLM 一次最多"记住"约 6-8 万汉字的上下文。每次 API 调用按输入+输出的 token 总数计费，所以裁剪历史 = 省钱。

⑧-a 虚拟线程 + OkHttp 阻塞式读取 SSE 数据流并发GlmLlmClient.java :43-78

这里有一个关键的技术桥接：

OkHttp 是阻塞 IO——readUtf8Line() 会一直等，直到收到一行新数据才返回。如果放在主线程里读，整个请求处理线程就被卡住了，无法处理其他请求。

解决方案：Java 21 虚拟线程。代码 Thread.startVirtualThread(() -> { ... }) 起一个虚拟线程，在这个虚拟线程里跑 OkHttp 的阻塞读取。虚拟线程不是操作系统线程（不占宝贵的线程池资源），可以同时创建成千上万个。每个 SSE 连接占一个虚拟线程，相互隔离，互不影响。

虚拟线程内部逐行读取 GLM API 返回的 SSE 数据流：

data: {"id":"chatcmpl-xxx","choices":[{"delta":{"content":"水"}}]}
data: {"id":"chatcmpl-xxx","choices":[{"delta":{"content":"煮"}}]}
data: {"id":"chatcmpl-xxx","choices":[{"delta":{"content":"鱼"}}]}
...
data: [DONE]

每读到一行就解析 JSON，提取 choices[0].delta.content（这就是 LLM 刚生成的一个 token / 一个字）。

虚拟线程（Virtual Thread）是 Java 21 引入的重大特性。传统的操作系统线程（Platform Thread）创建和切换成本很高，一个 Spring Boot 应用通常只有 200 个线程可用。虚拟线程由 JVM 管理而非操作系统管理，创建成本几乎为零。这意味着每个 SSE 长连接可以独占一个虚拟线程，同时有 1000 个用户在问问题也不会耗尽线程池。
⑧-b Sinks + Reactor Flux —— 阻塞IO → 非阻塞反应式桥接GlmLlmClient.java :69-74

这是整个服务最精妙的一行代码。

Spring WebFlux 的 Controller 返回 Flux<String>，意味着它期望一个非阻塞的反应式管道。但 OkHttp 是阻塞 IO。如何把这两者连起来？

答案：Sinks.Many（反应式水槽）+ 虚拟线程。Sinks.Many 就像一个"水管"——虚拟线程在管子一头往里灌水（sink.emitNext("水")），Reactor Flux 在管子另一头接水（前端收到 SSE 消息）。

把这个类比成外卖配送：OkHttp 阻塞读 = 厨房做饭（慢，要等）；虚拟线程 = 外卖骑手（等在厨房门口，做完一个菜就取走）；Sinks.emitNext = 骑手把菜递给前台；Reactor Flux = 前台实时把菜摆上顾客的桌子。顾客（前端）看到的是一道接一道菜上桌，不需要等全部做好。
为什么不直接用 WebClient（Spring 的非阻塞 HTTP 客户端）替代 OkHttp？技术上可以，但 OkHttp 的连接池管理、超时控制、重试机制更成熟。而且虚拟线程出现后，阻塞 IO 和非阻塞 IO 的性能差距已经微乎其微——虚拟线程让阻塞代码也拥有了非阻塞的并发能力。这就是"用最简单的代码达到最好的效果"。
